# 18. RAG 架构与索引构建：给大模型配"开卷考试"的资料员

### 一句话总结

RAG（检索增强生成）在模型生成答案前，先从外部知识库**检索相关文档片段**，注入到 prompt 中，解决大模型"知识截止日"、"私有数据盲区"和"幻觉"三大问题。

### 前置知识

- **第2天 Transformer 生成**：自回归 token-by-token 生成
- **第8天 Embedding 模型**：将文本映射为向量
- **第16天 量化技术**：embedding向量数据库也常需量化

### 核心概念（详细解释）

#### RAG 为什么需要存在？

大模型三大缺陷：

1. **知识截止日**：训练数据有截止日期
2. **私有数据盲区**：不知道公司内部规定
3. **幻觉**：一本正经地胡说八道

类比：考试时开卷——不要求学生背下所有知识，给一本资料书让他查。RAG就是给大模型配了"图书管理员"。

#### RAG 基本流程

```
// 代码块
索引阶段（离线）：文档加载 -> 切片 -> 向量化 -> 存入向量数据库
检索阶段（在线）：用户问题 -> 向量化 -> 相似度搜索 -> Top-K文档块
生成阶段（在线）：拼接上下文+问题 -> LLM生成答案
```

#### 索引构建详解

**文档切片（Chunking）**：

| 策略 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Fixed-size | 固定长度 | 简单 | 可能切断语义 |
| Sentence | 按句子 | 语义完整 | 长度不均 |
| Recursive | 递归切分 | 平衡 | 需调参 |
| Semantic | 按语义相似度 | 最优 | 计算量大 |

切片大小经验值：

- 通用知识：512-1024 tokens
- 技术文档：2048-4096 tokens
- 法律/合同：128-256 tokens

类比：切片像把教科书拆成卡片。太大检索不精确，太小丢失上下文。512 tokens约一段话，是好的平衡点。

**向量化与存储**：

```Python
// 代码块
from sentence_transformers import SentenceTransformer
import faiss

# 1. 加载embedding模型
embedder = SentenceTransformer('BAAI/bge-large-zh-v1.5')

# 2. 向量化文档
chunks = ["第一段文本...", "第二段文本...", ...]
embeddings = embedder.encode(chunks)

# 3. 存入向量数据库
index = faiss.IndexFlatIP(embeddings.shape[1])
index.add(embeddings.astype('float32'))

# 4. 检索
query_emb = embedder.encode(["用户问题"])
scores, indices = index.search(query_emb.astype('float32'), k=5)
```

#### Embedding 模型选择

| 模型 | 维度 | 语言 | 特点 |
| --- | --- | --- | --- |
| text-embedding-ada-002 | 1536 | 英文 | OpenAI |
| BGE-Large-zh-v1.5 | 1024 | 中文 | 智源，中文最优 |
| M3E-Large | 1024 | 多语言 | 性价比高 |
| GTE-Qwen2 | 1536 | 中文 | 通义千问 |

#### 生成模板

```
// 代码块
根据以下上下文回答问题。如果无法找到答案，请说"我不知道"。
上下文：{context}
问题：{question}
答案：
```

### 实际案例

#### 企业知识库RAG

- 10万页内部文档，512 tokens切片
- BGE-Large-zh-v1.5 + FAISS
- 准确率85%+，响应<3秒

#### ChatGPT浏览功能

本质就是RAG：搜索引擎检索网页 -> 提取内容 -> 注入prompt -> GPT-4生成

### 常见误区

- **RAG不需要训练模型**：需调参（切片大小、Top-K、prompt模板）
- **向量检索就是精确匹配**：是语义相似度匹配，不是关键词匹配
- **RAG能完全消除幻觉**：显著减少，但检索文档有误时仍可能幻觉
- **切片越小越好**：太小丢上下文，太大引噪声

### 为什么重要

1. 大模型落地必备：几乎所有企业级应用都依赖RAG
2. 幻觉杀手：引入外部知识源
3. 知识实时性：外部知识库可随时更新

## 19. 向量检索与重排序：从语义搜索到精准检索

### 一句话总结

向量检索解决"语义相似度搜索"问题，ANN 算法将 O(N) 的暴力搜索加速到 O(log N)，Re-Ranker 用交叉编码器对初筛结果做精细化排序，混合检索结合关键词和向量搜索取长补短。

### 前置知识

- **第8天 Embedding 模型**：文本到向量的映射
- **第18天 RAG 架构**：检索是RAG核心环节
- **第16天 量化技术**：向量索引也常需量化

### 核心概念（详细解释）

#### 近似最近邻搜索（ANN）

精确最近邻搜索（Brute Force）复杂度 O(N)，百万级向量需秒级响应。ANN 通过索引结构加速到 O(log N)。

类比：百万本书中找最相关的5本。暴力搜索是逐本翻阅，ANN是先看目录索引快速定位。

#### HNSW（分层导航小世界图）

类比：城市导航。先走高速公路（高层）快速到达附近城市，再走主干道（中层），最后走小路（底层）找到精确位置。

```Python
// 代码块
import hnswlib

dim = 1024
index = hnswlib.Index(space='cosine', dim=dim)
index.init_index(max_elements=1000000, ef_construction=200, M=16)
index.add_items(embeddings)
labels, distances = index.knn_query(query_embedding, k=10)
```

关键参数：

- M：节点最大连接数，越大精度越高
- ef_construction：建图搜索深度
- ef_search：查询搜索深度

#### FAISS 算法对比

| 算法 | 原理 | 精度 | 速度 | 适用场景 |
| --- | --- | --- | --- | --- |
| Flat | 暴力搜索 | 100% | O(N) | <10K |
| IVF | 倒排索引 | 高 | O(sqrt(N)) | 百万级 |
| HNSW | 分层图 | 高 | O(log N) | 百万级 |
| PQ | 乘积量化 | 中 | O(1) | 亿级 |
| IVF+PQ | 聚类+量化 | 中 | O(sqrt(N)) | 十亿级 |

#### Re-Ranker 模型

向量检索是"粗筛"（embedding相似度），Re-Ranker是"精筛"（交叉注意力）。

类比：向量检索像搜索引擎的"相关度排序"（快但粗），Re-Ranker像"人工审核"（慢但精）。

```Python
// 代码块
from sentence_transformers import CrossEncoder

reranker = CrossEncoder('BAAI/bge-reranker-large')
scores = reranker.predict([
    ["用户问题", "文档1"],
    ["用户问题", "文档2"],
    ["用户问题", "文档3"],
])
# 按分数重新排序
```

常用模型：

- **Cross-Encoder**：query+document拼接输入BERT，输出相关性分数
- **ColBERT**：token-level交互计算相关性
- **RankLLM**：用大模型做排序，效果最好但成本高

#### 混合检索（Hybrid Search）

向量检索擅长**语义匹配**，关键词检索（BM25）擅长**精确匹配**。混合检索=两者结合。

```
// 代码块
用户问题 ->
  |- 向量检索 -> Top-K（语义匹配）
  |- BM25检索 -> Top-K（关键词匹配）
  |- 归一化分数
  |- RRF融合排序 -> 最终Top-K
```

**RRF（Reciprocal Rank Fusion）**：

    RRF(d) = sum over retrievers r: 1 / (k + rank_r(d))

k是平滑参数（通常60）。RRF的优点是不需要分数归一化，只依赖排名。

### 实际案例

#### 企业知识库检索优化

某公司RAG系统检索优化历程：

1. 纯向量检索：准确率70%
2. 向量+Re-Ranker：准确率82%
3. 混合检索+Re-Ranker：准确率89%

#### LangChain/LlamaIndex 的检索流程

两个主流RAG框架都支持：

1. 向量检索（默认）
2. 混合检索（BM25+向量）
3. Re-Ranker（可选）

### 常见误区

- **向量检索一定能找到最相关的文档**：ANN是近似算法，可能遗漏
- **Re-Ranker越多越好**：Re-Ranker计算成本高，通常只对Top-10到Top-50重排序
- **混合检索一定比单一检索好**：如果向量检索和关键词检索结果高度重合，混合检索收益有限
- **FAISS是最好的向量数据库**：FAISS是库不是数据库，生产环境通常用Milvus、Qdrant等

### 与其他知识点的关系

- 前驱：Embedding模型（第8天）、RAG架构（第18天）
- 后继：高级RAG（第20天）依赖更精细的检索

### 为什么重要

1. 检索质量决定RAG效果："垃圾进，垃圾出"
2. 工业界标配：所有RAG框架都支持混合检索+Re-Ranking
3. 搜索技术新范式：向量检索正在取代传统关键词搜索

## 20. 高级 RAG 策略：从简单检索到知识图谱增强

### 一句话总结

基础 RAG 的"分块->向量化->检索->生成"套路在复杂场景下效果有限，高级 RAG 通过**多跳检索、HyDE 假设文档、知识图谱增强、长上下文 RAG** 等技术，显著提升复杂推理和专业知识问答的效果。

### 前置知识

- **第18天 RAG 架构**：基础检索增强生成流程
- **第19天 向量检索与重排序**：ANN、Re-Ranker、混合检索
- **第17天 长上下文处理**：百万级 token 的处理能力

### 核心概念（详细解释）

#### 基础 RAG 的局限

1. **单跳检索**：只检索一次，可能遗漏关键信息
2. **切片粒度问题**：固定切片无法适应不同问题
3. **语义理解局限**：embedding 无法理解复杂逻辑关系
4. **长文档丢失上下文**：关键信息可能在文档不同位置

#### 多跳检索（Multi-hop Retrieval）

对于需要多步推理的问题："A 公司的 CEO 的配偶毕业于哪所大学？"

基础RAG一次性检索很难找到答案。多跳检索：

```
// 代码块
第1轮："A公司的CEO是谁？" -> 检索到CEO名字
第2轮："CEO的配偶是谁？" -> 检索到配偶名字
第3轮："配偶毕业于哪所大学？" -> 得到答案
```

两种实现方式：

- **迭代式**：每轮用上一轮结果重构查询，多次检索
- **并行式**：同时生成多个子查询，并行检索后合并

类比：基础RAG像翻一次字典，多跳检索像查字典时看到一个词条，发现需要再查另一个词条，连续查多次。

#### HyDE（Hypothetical Document Embeddings）

核心思想：**让大模型先"假设"一个答案，然后检索与假设答案最相似的文档。**

类比：考试时先猜答案，再去书上找依据。

流程：

1. 用户问题 -> LLM生成假设答案
2. 假设答案 -> embedding
3. 用假设答案的embedding检索文档
4. 用检索到的文档生成最终答案

**为什么有效？** 大模型生成的假设答案通常比用户问题"更接近"知识库中的真实文档。因为文档是用"答案式"语言写的，而用户问题是用"提问式"语言写的。

#### 知识图谱增强 RAG（GraphRAG）

将文档知识抽取为**知识图谱**（实体-关系-实体三元组），检索时基于图结构进行推理。

```
// 代码块
文档 -> NER + 关系抽取 -> 知识图谱
用户问题 -> 图查询 -> 相关子图 -> LLM生成
```

优势：

- **多跳推理**：通过图路径发现间接关系
- **结构化信息**：比文本块更精确
- **全局理解**：理解文档集整体知识结构

#### 长上下文 RAG

当文档非常长（书籍、法律文件）时，传统切片检索效果差。长上下文RAG直接让模型读取完整长文档：

- 依赖长上下文模型（Claude 200K、Gemini 1M）
- 依赖FlashAttention和NTK缩放
- 检索时直接返回完整文档而非切片

#### 其他高级策略

| 策略 | 原理 | 适用场景 |
| --- | --- | --- |
| Self-RAG | LLM自我反思检索结果质量 | 减少幻觉 |
| CRAG | 检索结果校正（正确/错误/未知） | 提高可靠性 |
| RAPTOR | 层次化摘要树构建 | 长文档理解 |
| HippoRAG | 基于海马记忆索引的图谱检索 | 知识整合 |

### 实际案例

#### 微软 GraphRAG

微软2024年开源的GraphRAG项目：

1. 从文档中抽取实体和关系，构建知识图谱
2. 用社区检测算法对图谱分群
3. 为每个社区生成摘要
4. 查询时：全局查询用社区摘要，局部查询用图遍历

效果：在长文档理解任务上显著优于基础RAG。

#### Multi-hop QA 系统

某法律问答系统：

- 问题："原告公司在2020年的专利申请数量是否超过了被告公司？"
- 需要多跳：先找原告公司专利数据，再找被告公司数据，最后比较
- 用多跳检索+Re-Ranker，准确率从55%提升到78%

### 常见误区

- **高级RAG一定比基础RAG好**：简单问题用基础RAG足够，高级策略增加延迟和成本
- **HyDE总是有效**：如果模型对领域不熟悉，假设答案可能误导检索方向
- **知识图谱很难维护**：实际上有很多自动化工具（LLM+NER）可以半自动构建
- **长上下文RAG不需要切片**：即使有1M上下文，切片检索仍然有助于聚焦相关信息

### 与其他知识点的关系

- 前驱：RAG架构（第18天）、向量检索（第19天）
- 平行：长上下文处理（第17天）是长上下文RAG前提
- 在Roadmap中：第五阶RAG与应用的高级策略

### 为什么重要

1. 专业领域问答的关键：医疗、法律、科研需要多跳推理和知识图谱
2. RAG效果的质变：从"能用"到"好用"
3. 大模型落地的天花板技术：决定企业级应用最高质量
