### 核心概念

#### 推理的瓶颈在哪？

大模型推理（尤其是自回归生成）有三个核心瓶颈：

##### 瓶颈1：KV Cache内存爆炸

```
// 代码块
什么是KV Cache？

  Transformer的自注意力机制需要计算：
  Attention(Q, K, V) = softmax(QK^T / √d) × V
  
  其中 Q、K、V 分别来自输入的Query、Key、Value
  
  自回归生成时，每生成一个新Token，需要：
  ├─ 当前Token的Q
  └─ 之前所有Token的K和V
  
  如果不缓存，每次都要重新计算所有历史Token的K和V → O(n²)复杂度
  如果缓存了，只需要计算当前Token的K和V → O(n)复杂度
  
  这就是KV Cache——把之前计算过的K和V存起来，避免重复计算

KV Cache有多大？

  以LLaMA-3-70B为例：
  ├─ 层数：80层
  ├─ 每层KV Cache：2 × seq_len × hidden_size × 2字节(FP16)
  ├─ hidden_size = 8192
  ├─ seq_len = 4096
  └─ 单层KV Cache = 2 × 4096 × 8192 × 2 = 134MB
  总KV Cache = 80 × 134MB = 10.7GB
  
  10.7GB！这只是一个用户的！
  如果同时服务100个用户 → 1070GB → 需要14张A100
  
  这就是为什么KV Cache是推理的核心瓶颈
```

##### 瓶颈2：动态序列长度

不同用户的输入长度不同（有人问100字的问题，有人问5000字）。传统方法需要按最长序列分配内存，短的序列浪费大量空间。

##### 瓶颈3：内存碎片

频繁分配和释放显存导致碎片化。40GB显卡可能只装得下35GB的计算——剩下的5GB被碎片"吃掉"了。

#### PagedAttention（vLLM的核心创新）

> 类比：操作系统的虚拟内存管理。

```
// 代码块
传统KV Cache管理（类似连续分配）：

  显存布局：
  ┌───────────────────────────────────────┐
  │ 请求A (2048 tokens)                    │
  │ ████████████████████████████████      │  ← 分配了2048的空间
  │                                        │
  │ 请求B (512 tokens)                     │
  │ ██████                                │  ← 分配了2048的空间，但只用了512
  │                                        │     ← 浪费了1536的空间！
  │ 请求C (1024 tokens)                    │
  │ ████████████                          │  ← 分配了2048的空间，但只用了1024
  │                                        │     ← 浪费了1024的空间！
  └───────────────────────────────────────┘
  
  问题：预分配最大长度 → 大量空间浪费

PagedAttention（类似分页管理）：

  显存布局：
  ┌───────────────────────────────────────┐
  │ Page 0  │ Page 1  │ Page 2  │ Page 3  │
  │ 请求A   │ 请求A   │ 请求B   │ 请求C   │
  │ (256tok)│ (256tok)│ (256tok)│ (256tok)│
  ├─────────┼─────────┼─────────┼─────────┤
  │ Page 4  │ Page 5  │ Page 6  │ Page 7  │
  │ 请求A   │ 请求A   │ 请求A   │ 请求C   │
  │ (256tok)│ (256tok)│ (256tok)│ (256tok)│
  ├─────────┼─────────┼─────────┼─────────┤
  │ Page 8  │ Page 9  │ Page 10 │ Page 11 │
  │ 请求A   │ 请求B   │ ...     │ ...     │
  │ (256tok)│ (256tok)│         │         │
  └───────────────────────────────────────┘
  
  每个Page固定大小（如256个Token的KV Cache）
  请求A用了8个Page（2048 tokens）
  请求B用了2个Page（512 tokens）→ 没有浪费！
  请求C用了4个Page（1024 tokens）→ 没有浪费！
  
  优势：
  ├─ 没有预分配浪费（按需分配Page）
  ├─ 没有内存碎片（Page是固定大小的）
  └─ 显存利用率从20-40%提升到接近95%
```

**PagedAttention的效果**：

- 显存利用率：从20-40% → 95%+
- 吞吐量：比传统方法提升2-4倍
- 能同时服务的用户数：提升3-5倍

#### 连续批处理（Continuous Batching）

> 类比：餐厅翻台率。传统方法是"一桌一桌服务"（静态批处理），vLLM是"有人点菜就开始服务，吃完了立刻接下一桌"（连续批处理）。

```
// 代码块
传统静态批处理：

  时间轴 →
  ┌─────────────────────────────────────────┐
  │ 请求A ████████████                     │ 生成12个Token
  │ 请求B ██████                           │ 生成6个Token（先完成）
  │ 请求C ██████████████████               │ 生成18个Token
  └─────────────────────────────────────────┘
  
  问题：请求B先完成了，但必须等A和C都完成才能接新请求
        → GPU空闲等待，浪费算力

连续批处理：

  时间轴 →
  ┌─────────────────────────────────────────┐
  │ 请求A ████████████                     │
  │ 请求B ██████→ 完成！请求D      ███████ │ ← B完成后立刻接D
  │ 请求C ██████████████████               │
  └─────────────────────────────────────────┘
  
  优势：GPU永不空闲，吞吐量提升10倍+
```

#### 推测解码（Speculative Decoding）

> 类比：考试时先快速答一遍草稿（小模型），再检查一遍正式答案（大模型）。如果草稿和正式答案一致，直接提交草稿（省时间）。

```
// 代码块
传统自回归解码：
  Token1 → Token2 → Token3 → Token4 → Token5
  每次都要跑一遍大模型（慢）

推测解码：
  步骤1：小模型（7B）快速生成5个候选Token
  [Token1, Token2, Token3, Token4, Token5]
  
  步骤2：大模型（70B）一次性验证这5个Token
  ├─ 如果全部正确 → 直接输出5个Token（省了4次大模型推理）
  ├─ 前3个正确，第4个错 → 输出前3个，从第4个开始重新生成
  └─ 全部错误 → 回退到传统方式
  
  效果：
  ├─ 如果小模型准确率80%：平均加速2-3倍
  ├─ 输出分布与大模型完全一致（数学保证）
  └─ 代价：需要额外的小模型推理开销
```

### 技术细节

#### vLLM 快速上手

```Python
// 代码块
from vllm import LLM, SamplingParams

# 加载模型（自动检测GPU）
llm = LLM(
    model="meta-llama/Llama-3-8B-Instruct",
    tensor_parallel_size=1,    # GPU数量
    max_model_len=8192,        # 最大序列长度
    gpu_memory_utilization=0.9, # GPU内存使用比例
    quantization=None,         # 量化选项: None, "awq", "gptq", "squeezellm"
)

# 配置采样参数
sampling_params = SamplingParams(
    temperature=0.8,    # 温度：越高越随机
    top_p=0.95,         # Top-P采样：保留累积概率95%的Token
    max_tokens=512,     # 最大生成长度
)

# 单次推理
output = llm.generate("Hello, how are you?", sampling_params)
print(output[0].outputs[0].text)

# 批量推理（连续批处理自动生效）
prompts = [
    "请解释什么是量子力学",
    "Write a Python function to sort a list",
    "什么是RAG系统？",
]

outputs = llm.generate(prompts, sampling_params)
for i, output in enumerate(outputs):
    print(f"=== Prompt {i+1} ===")
    print(output.outputs[0].text)
    print(f"生成Token数: {len(output.outputs[0].token_ids)}")
    print()
```

### 常见误区

**❌ 误区1：推理框架只是"加速"**
推理框架不仅加速，还解决内存管理、并发处理、量化支持、API服务等工程问题。直接用HuggingFace Transformers做生产服务，效率极低。

**❌ 误区2：vLLM一定比llama.cpp快**
不一定。在单用户、短序列场景下，llama.cpp因为C++实现，可能比vLLM更快。vLLM的优势在高并发场景下的吞吐量。

**❌ 误区3：量化一定导致精度下降**
INT8量化精度损失通常<1%，几乎可以忽略。INT4量化损失1-3%，在可接受范围内。关键是选择合适的量化方法（如AWQ比普通INT4量化效果好）。

**❌ 误区4：GPU越多越快**
不一定。多GPU推理需要GPU间通信，如果通信带宽不够（如没有NVLink），反而可能变慢。需要合理配置张量并行和流水线并行。

### 为什么重要

推理框架是**大模型产品化的核心引擎**：

- **成本**：推理占大模型应用90%以上的计算成本，优化推理=省钱
- **体验**：用户能容忍的等待时间是秒级，推理框架直接决定了响应速度
- **规模**：服务百万级用户需要高效的批处理和资源管理
- **生态**：vLLM（LMSYS开源）已成为开源推理框架的事实标准

**关键认知**：选择合适的推理框架对性能和成本影响巨大。vLLM适合大规模生产，llama.cpp适合边缘/个人部署，TensorRT-LLM适合NVIDIA极致优化。

### 小练习

**练习1**：解释PagedAttention为什么能把显存利用率从30%提升到95%。

**答案提示**：传统方法预分配最大序列长度的连续内存，短序列浪费大量空间。PagedAttention把KV Cache切成固定大小的Page，按需分配。序列变长时只需分配新Page，不需要重新分配整个数组。这消除了预分配浪费和内存碎片。

**练习2**：你有1张A100（80GB），需要部署Llama-3-70B模型服务。请计算：

1. 模型权重需要多少显存？（FP16）
2. KV Cache可用多少显存？
3. 理论上能同时服务多少用户？（假设平均序列长度2048）

**答案提示**：

1. 70B × 2字节(FP16) = 140GB → 1张80GB A100不够，需要量化
2. 如果用INT4量化：70B × 0.5字节 = 35GB，剩余80-35=45GB用于KV Cache
3. 单用户KV Cache（2048 tokens）：80层 × 2 × 2048 × 8192 × 2字节 ≈ 5.3GB

   理论用户数：45/5.3 ≈ 8个并发用户
