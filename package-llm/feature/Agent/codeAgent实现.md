# mini-claude-code（施工中）

## 产品解析

Claude Code是一款AI Coding工具，内置一个LLM驱动的Agent，用户可以通过自然语言与其对话并下发任务，Agent能自主规划，操作本地文件，完成编程任务。下面从4个层面解析Claude Code的产品能力。

### Agent

用户向Agent发送指令，Agent能自主规划完成任务，具体来说，它包含如下产品能力：

- **多种执行模式**：包含Default、Auto-accept edits、Plan mode模式，其中Default模式下，Agent在文件编辑和 shell 命令前会询问用户，Auto-accept edits模式下，Agent不询问直接编辑文件，但会询问命令。Plan mode模式下，Claude 仅使用只读工具。
- **任务列表**：Agent能自主规划执行计划，拆解为多个子任务，并实时更新子任务完成情况。
- **文件读写**：Agent能自主读写文件
- **shell命令执行**：Agent能自主执行shell命令
- **Skills**：Agent能通过技能扩展能力，自主读取技能信息，并按技能要求执行任务
- **MCP**：Agent能通过MCP扩展能力，装载MCP工具并按需执行
- **Rules**：Agent能通过Rules扩展能力，按需读取rule信息，并按rule要求执行任务
- **SubAgents**：Agent能通过subAgents扩展能力，调用子Agent执行子任务，增加并发度，且隔离上下文
- **background task**：Agent能将shell命令执行任务置于后台
- **上下文压缩**：Agent能自动压缩上下文，实现无限上下文窗口，执行超复杂任务

### 扩展配置

各类配置：

- **模型配置**：不同厂商的不同模型
- **command**：预置prompt，配置快捷指令
- **hook**：在Agent执行的各个生命周期执行用户自定义的确定性脚本
- **Skills、MCP、Rules、SubAgent**：四类agent扩展能力的配置
- **plugin**：包含其它所有配置的总和，一套完整的配置方案。

### 会话管理

用户通过与Agent对话来完成任务，以下为与会话相关的功能：

- **版本回退**：用户每一次输入就是一个检查点，可以将代码和对话信息回退到任意一个检查点
- **会话切换**：用户可以开启多个会话并切换，不同会话的上下文互相隔离
- **多模态输入**：支持文本和图片输入
- **文件引用**：支持直接引用指定本地文件给Agent
- **command输入**：支持预置prompt，通过command快捷输入
- **background task**：支持手动将任务置于后台
- **会话fork**：支持复制当前会话的上下文并创建一个新的会话
- **上下文压缩**：支持按指定要求手动压缩当前会话上下文

### 交互

- **交互形式**：支持四种交互形式，包括终端terminal、浏览器web、浏览器插件、桌面应用desktop

## 架构设计

### 系统分层架构图

首先进行总的架构设计，使用分层架构，按职责进行垂直切分，从下往上分别为：

1. **基础设施**：与逻辑无关的公共基础设置，如日志系统、数据访问系统、Agent测试系统等
2. **Agent Core**：Agent运行的核心逻辑
3. **业务逻辑**：Agent与用户的交互逻辑，负责启动Agent，向Agent发送指令，以及获取Agent运行时信息并转化为用户看到的信息
4. **接入**：作为交互层与业务逻辑的中间层，负责配置信息的获取处理，负责数据的持久化等
5. **交互**：负责用户的交互界面

### Agent Core

1. **BaseAgent**：Agent运行的核心逻辑。
2. **事件通信**：Agent与外部交互的逻辑。Agent需要暴露其运行过程与运行结果给外部展示，外部可以打断其运行过程，以及输入新的指令。因此通过一个事件驱动（Event-Driven）+ 观察者模式（Observer）+ 命令模式（Command）组合的通信层链接外部与Agent。
3. **状态管理**：负责Agent运行时中断与恢复。由于Agent可以中断并且重新恢复运行，在设计时，需要设计持久化状态，并且能载入这些状态继续运行。但这些状态如何存储，Agent无需关心，由外部实现。
4. **配置注入**：Agent所需运行配置的校验与注入。

> 如果把一个Agent看做是一台电脑，其绝对核心就是CPU+内存，CPU负责信息处理，内存负责管理CPU要处理的信息。对应到Agent中，CPU就是LLM，内存就是Context。因此Agent模块设计的核心在于如何处理Context将其送入LLM执行，以及如何解析和处理LLM的执行结果并调用tool完成任务，其它的如Skills、SubAgent等都作为外部模块，通过扩展tools的方式接入。

### 业务逻辑

1. **会话管理**：负责外部与Agent的会话管理，控制Agent的运行，将Agent的运行信息转化为用户可见的格式化信息。
2. **配置管理**：负责配置的校验
   - 模型调用服务提供商、模型选择、模型参数、密钥
     - 这里支持硅基流动和美团两家服务提供商，可用模型列表需要手动配置，密钥由外部提供，需要发送一条测试消息验证密钥可用性
   - MCP配置、MCP连接、MCP工具列表选择

## 详细设计

### Agent Core

Agent core包提供创建Agent的能力，支持配置Agent的系统提示词、工具列表，以及LLM调用接口参数，Agent包含context、tools、llm三个关键对象。

#### LLM

**核心功能**

支持LLM调用和流式响应，需要实时将流式响应的分块内容返回，响应结束后需要返回拼接后的完整内容。从环境变量中读取接口url、apikey。

**关键对象定义**

**StreamEvent**

包含以下六个流式响应事件：

| 事件 | 说明 |
| --- | --- |
| `stream-start` | 流式开始 |
| `text-delta` | 返回增量文本 |
| `reasoning-delta` | 返回增量推理文本 |
| `tool-call` | 返回工具调用 |
| `tool-call-args-delta` | 返回增量工具调用参数 |
| `stream-end` | 流式结束 |

> 注意，在流式结束时，返回结束原因和所有分块内容拼接后的完整内容。

#### Context

**核心功能**

Context要操作的核心数据是message，包括system message、user message、assistant message、tool message。多条message拼接为一个message列表，整个列表便是agent的上下文。由于消息内容有多种类型，包括图片、文字、推理文字、工具调用、工具结果，因此消息内容使用Part定义，每条消息的消息内容可以由多个Part组成。Context需要负责任意message的增删查改以及上下文的压缩。

**关键对象定义**

- **Part**：用于表示不同含义或格式的内容，包括图片、文字、推理文字、工具调用、工具结果
- **Message**：用于表示一条消息，包括system message、user message、assistant message、tool message，每条消息的内容由多个Part对象组成。每条message还有一个metadata属性，用于记录一些额外的元信息，比如tool的原始输出，user的原始输入等。
- **Context**：表示Agent的上下文，提供通用的message的增删改查能力，以及一系列上下文处理方法，目前只需包含上下文缩减方法即可。除此以外，还需包含一些信息的记录，包括当前上下文token长度等。

**上下文缩减**

Agent的上下文窗口是有限制的，并且当上下文达到一定长度时会出现上下文腐烂问题，因此需要在特定时机缩减上下文，使得Agent可以正常持续运行。上下文缩减包含压缩和摘要两种策略，这里只实现摘要策略。

- **实施时机**：当上下文长度达到LLM上下文窗口的50%时
- **实施方式**：取message列表前50%的内容，使用LLM总结并输出结构化的摘要，将其与后50%的内容进行拼接，构成新的上下文。

#### Tools

**核心功能**

Tools操作的核心数据是tool，负责tool的动态加载、卸载和执行，Agent只会使用已加载的工具。除此以外，我们还需定义一组Agent内置的工具列表，包括：

- **Bash执行**
- **读文件**
- **写文件**
- **编辑文件**

#### Agent

**核心功能**

Agent核心功能是整合LLM、Context和Tools模块，处理各模块之间的数据传递，然后调用各模块实现自主完成任务的流程。Agent执行是一个闭环的循环过程。

**Agent核心执行流程**

为了实时暴露其运行过程与运行结果给外部，定义了Agent执行生命周期，并通过事件广播。包括如下几个生命周期：

1. Agent循环开始
2. LLM调用开始
3. 首次响应
4. 响应更新：需要暴露本次LLM调用返回的增量数据，其格式可以复用StreamEvent
5. LLM调用结束：需要暴露本次LLM调用返回的全量数据
6. 执行工具开始（非必须）
7. 执行工具结束（非必须）
8. Agent循环结束

**执行中断**

Agent执行过程可能会被打断，需要记录中断时的状态，并支持恢复运行。

- **中断节点**有两个：
  1. LLM响应时
  2. 工具执行时
  
  其中LLM响应时中断既可以是网络异常引起，也可以是用户主动中断。而工具执行时只能由用户主动中断。

- **恢复策略**有两种：
  1. 从中断处恢复运行
  2. 保留当前状态，用户发起新指令

- **分情况执行恢复策略**：
  1. 如果由用户主动中断，表明是用户认为Agent执行有误，因此只能用户重新发起指令继续。
  2. 如果是网络异常引起，则用户可以选择从中断处恢复运行，也可以继续发起新指令。

> 中断通过一个 `AbortController` 对象实现，针对LLM响应会在每次异步接收chunk时检测是否有中断信号，针对工具执行，向工具执行函数传递 `AbortController` 对象，由工具函数内部自行判定终止。

**执行恢复**

执行恢复指从中断处继续执行任务：

1. 如果是从中断处恢复运行，需要使用模型的补全模式，让模型续写assistant回复内容
2. 如果是用户发起新指令，需要在指令前拼接中断原因，包括用户主动中断回复以及用户主动中断工具执行

**权限控制**

Agent可以通过bash工具执行bash命令，也可以通过write-file和edit-file工具修改文件，因此Agent需要接入权限控制能力来从外部控制其是否可执行特定的工具。

目前默认有三种情况会受到权限控制：

1. bash工具执行 `rm`、重定向等涉及文件修改的命令以及其它外部自定义的命令
2. write-file工具执行
3. edit-file工具执行

有两种权限模式：

1. **dangerous mode**：Agent可任意执行工具
2. **target mode**：外部指定的工具以及bash工具的指定命令不用受权限控制

> 权限控制逻辑：当触发权限控制时，阻塞执行并向外部发送信号，当外部给出同意信号后，再执行工具。

**后台任务**

Agent执行bash工具时，该命令可能运行很长时间，且Agent后续任务不立即依赖此任务的结果，Agent可以将该bash工具调用置为后台任务，在调用工具时通过指定参数实现。Agent有一个后台任务管理器，能通过工具调用看到所有的后台任务，主动查询后台任务当前的状态和输出。后台任务结束以后，会在LLM调用前将后台任务执行结果拼接在上下文里让Agent感知。

除此以外，外部可以主动将bash工具执行添加为后台任务，此时bash工具应该返回该命令执行被用户置为后台任务，任务id是多少。

**关键对象定义**

- **BaseAgent**：包含完整的Agent功能，支持外部配置和修改系统提示词、工具列表等。包含一个 `execution_status` 信息，表明当前处于待执行指令、执行中、执行中断三个运行状态。

> 随着Agent的运行，其context以及其它运行信息可能会变化，因此需要有一个state对象，包含Agent运行时的所有信息，该state对象可被导出，也可以被导入以恢复Agent的状态。
