### 二、项目简介

**一句话定位**：在工具输出、日志、RAG 结果、文件等内容进入 LLM 之前，先压缩一遍。60-95% 的 Token 减少，答案质量不变。

Headroom 是一个专为 AI Agent 设计的**上下文压缩层（Context Compression Layer）**。它解决的核心问题是：AI Agent 运行过程中，工具返回的 JSON、日志、RAG 检索块、代码文件等内容包含大量冗余，导致 Token 消耗飙升、成本失控、甚至超出上下文窗口限制。

Headroom 不是简单的截断或摘要，而是一套**结构感知、内容类型路由、可逆的智能压缩系统**——压缩后原始数据本地保留，LLM 可通过 `headroom_retrieve` 工具按需取回，确保信息零丢失。

### 三、核心功能详解

#### 3.1 六种压缩算法，智能路由

| 算法 | 适用内容 | 技术原理 |
| --- | --- | --- |
| **SmartCrusher** | JSON 数据 | 统计分析 + Kneedle 算法，保留异常值和变更点 |
| **CodeCompressor** | 代码 | AST 感知切片（tree-sitter），保留关键结构 |
| **Kompress-base** | 文本/散文 | 基于 HuggingFace ModernBERT 模型训练的语义压缩 |
| **Image Compressor** | 图片 | ML 路由 + OCR，40-90% 缩减 |
| **CacheAligner** | 前缀稳定 | 动态内容检测（UUID、时间戳等），提升 KV Cache 命中率 |
| **IntelligentContext** | 上下文评分 | BM25 + Embedding 混合相关性评分 |

##### SmartCrusher（JSON 压缩器）

工具调用的返回值通常是 JSON，包含大量与当前问题无关的字段。SmartCrusher 分析 LLM 的上一条查询，提取相关字段，丢弃无关结构：

- **Kneedle 算法**：自适应确定保留项数 K
- **异常值保护**：> 2 标准差的数值项永不删除
- **错误项保护**：包含 error/failed 的项永不删除
- **相关性评分**：BM25 + Embedding 混合评分保留相关项
- **锚点分配**：前 K/后 K 项 + 中间重要项的动态分配

示例：100 条日志中找 FATAL 错误，从 10,144 token 压到 1,260 token（87% 节省），同样找到了那条错误。

##### CodeCompressor（AST 感知代码压缩）

不是字符串截断，而是先解析代码的 AST（抽象语法树），然后：

- 保留所有函数/类的签名
- 折叠函数体（用占位符替代）

结果：Agent 能看到完整的代码结构，但不用读每一行实现细节。支持 Python、JavaScript、Go、Rust、Java、C++。

##### Kompress-base（文本压缩）

针对纯文本的压缩使用 HuggingFace 上的 Kompress-base 模型，基于 ModernBERT 做 token 分类，判断哪些句子是冗余的可以删掉。

##### CacheAligner（KV 缓存优化）

这是一个经常被忽视的细节：Anthropic 和 OpenAI 都有 prompt 缓存（prefix caching），但如果 system prompt 里有动态内容（时间戳、UUID、session token），每次前缀都不一样，缓存就白费了。CacheAligner 会把这些动态内容提取出来，移到 prompt 末尾，稳定前缀，让缓存真正命中。

#### 3.2 CCR 可逆压缩（Compress-Cache-Retrieve）

这是 Headroom 最核心的创新：**压缩不是截断，原始数据从不删除**。

```
// 代码块
原文 ──────────── 压缩 ──────────→ LLM
  │                                  │
  └── 存入本地 CCR 索引              │
       (按 trace_id 索引)            │
                                     │ 需要更多细节时
                                     ↓
                              headroom_retrieve("trace_id", "函数实现")
                                     │
                                     ↓
                              从本地索引取回原文片段
```

压缩后的数据附带 CCR 哈希，LLM 可以通过 `headroom_retrieve` 按需检索原始内容。这解决了"压缩可能漏掉关键信息"的顾虑——模型本身有能力判断什么时候需要补充细节。

#### 3.3 跨 Agent 共享记忆

Claude Code、Codex、Gemini 等不同 Agent 之间可以共享压缩后的上下文存储，自动去重，实现真正的多 Agent 协作。按 user → session → agent → turn 四个层级做隔离，不会互相污染。

```Shell
// 代码块
# 所有 Agent 走同一个代理，自动共享记忆
headroom proxy --port 8787 --memory
```

#### 3.4 headroom learn — 从失败中自动学习

当 Agent 会话失败（任务未完成、LLM 多次重试、上下文超限），`headroom learn` 会：

1. 分析失败的 Agent 会话日志
2. 挖掘重复出现的错误模式
3. 自动将修正建议写入 `CLAUDE.md` / `AGENTS.md` / `GEMINI.md`

这是一个**自我进化的反馈循环**——Agent 踩过的坑，下次启动时就带着修正上场了。

#### 3.5 生产级基准验证

**实际工作负载节省**：

| 工作负载 | 压缩前 Token | 压缩后 Token | 节省 |
| --- | --- | --- | --- |
| 代码搜索（100 结果） | 17,765 | 1,408 | **92%** |
| SRE 故障调试 | 65,694 | 5,118 | **92%** |
| GitHub Issue 分类 | 54,174 | 14,761 | **73%** |
| 代码库探索 | 78,502 | 41,254 | **47%** |

**精度保持**：

| 基准测试 | 类别 | 样本数 | 基线 | Headroom | 变化 |
| --- | --- | --- | --- | --- | --- |
| GSM8K | 数学 | 100 | 0.870 | 0.870 | ±0.000 |
| TruthfulQA | 事实 | 100 | 0.530 | 0.560 | +0.030 |
| SQuAD v2 | QA | 100 | — | 97% | 19% 压缩 |
| BFCL | 工具 | 100 | — | 97% | 32% 压缩 |

关键结论：**去掉冗余内容不会降低答案质量，有时反而更好**——LLM 不再被不相关内容干扰。

### 四、使用方式

#### 4.1 安装

```Shell
// 代码块
# 方式1：pip 安装（推荐）
pip install "headroom-ai[all]"          # 完整功能
pip install "headroom-ai[proxy]"        # 仅代理模式
pip install "headroom-ai[ml]"           # 含 ML 压缩模型

# 方式2：npm 安装（TypeScript）
npm install headroom-ai

# 方式3：Docker
docker pull ghcr.io/chopratejas/headroom:latest

# 方式4：pipx（隔离安装）
pipx install --python python3.13 "headroom-ai[all]"
```

#### 4.2 方式一：Library 模式（代码内嵌）

```Python
// 代码块
from headroom import compress

# 最简单的使用方式
result = compress(messages, model="gpt-4o")
print(f"节省 {result.tokens_saved} tokens ({result.compression_ratio*100:.1f}%)")

# SDK 包装模式
from headroom import HeadroomClient, OpenAIProvider
from openai import OpenAI

client = HeadroomClient(
    original_client=OpenAI(),
    provider=OpenAIProvider(),
    default_mode="optimize",
)
response = client.chat.completions.create(model="gpt-4o", messages=messages)
```

TypeScript 版本：

```TypeScript
// 代码块
import { compress } from 'headroom-ai';
const result = await compress(messages, { model: 'claude-opus-4-5' });
// result.messages 就是压缩后的版本
```

#### 4.3 方式二：Proxy 模式（零代码改动）

```Shell
// 代码块
# 启动代理
headroom proxy --port 8787

# 把你的 ANTHROPIC_BASE_URL 指向本地代理
export ANTHROPIC_BASE_URL=http://localhost:8787

# 其他不变，代码不用动
```

#### 4.4 方式三：Agent Wrap（一行命令包装现有 Agent）

```Shell
// 代码块
# 直接 wrap Claude Code，自动压缩所有上下文
headroom wrap claude

# 带记忆功能
headroom wrap claude --memory

# 同样支持 Cursor、Codex、Aider
headroom wrap cursor
headroom wrap codex
headroom wrap aider
headroom wrap copilot
```

#### 4.5 方式四：MCP Server

```Shell
// 代码块
headroom mcp install
```

安装后，MCP 客户端会多出三个工具：

- `headroom_compress` — 压缩内容
- `headroom_retrieve` — 按需取回原文
- `headroom_stats` — 查看压缩统计

配置示例（claude_desktop_config.json）：

```JSON
// 代码块
{
  "mcpServers": {
    "headroom": {
      "command": "headroom",
      "args": ["mcp"]
    }
  }
}
```

### 五、落地实践场景

#### 场景1：AI 编码 Agent 日常使用

**痛点**：每天跑 Claude Code / Cursor / Codex，工具输出大量 JSON，上下文经常爆，Token 费用高企。

**方案**：用 `headroom wrap` 一行命令包装 Agent，自动压缩工具输出。实测节省 50-90% Token，且不影响代码生成质量。

**推荐模式**：Agent Wrap + Memory

#### 场景2：RAG 系统优化

**痛点**：检索出的文档块大量冗余，上下文窗口被无关内容占满，LLM 被干扰导致回答质量下降。

**方案**：在 RAG 检索结果送入 LLM 之前，用 Library 模式调用 `compress()`，SmartCrusher 和 Kompress-base 自动去冗余。

**推荐模式**：Library 模式

#### 场景3：SRE/运维日志分析

**痛点**：事故调试时，日志、堆栈跟踪、指标数据混合输入，动辄 6 万+ Token，关键异常信息淹没在噪声中。

**方案**：Headroom 的 SmartCrusher 自动保留异常值和错误关键词（FATAL/ERROR/failed），过滤正常 passing 的噪声。65,694 token 压缩至 5,118，节省 92%，且关键信息反而更突出。

**推荐模式**：Proxy 模式（对现有运维系统零侵入）

#### 场景4：多 Agent 协作团队

**痛点**：同时使用 Claude Code、Codex、Cursor，但三个 Agent 的记忆完全隔离——在 Claude 里解决的坑，换到 Codex 得重新交代。

**方案**：启动 `headroom proxy --port 8787 --memory`，所有 Agent 走同一个代理，共享压缩后的记忆存储，自动去重。

**推荐模式**：Proxy + Memory

#### 场景5：成本优化/企业级降本

**痛点**：大量 Agent 并发运行，Token 消耗巨大，月度 API 费用失控。

**方案**：部署 Headroom 代理服务，所有 Agent 请求经代理压缩后发送。按最保守 47% 的压缩率估算，月度 API 费用直接减半。

**推荐模式**：Docker 部署 Proxy 模式

### 七、个人评价和建议

#### 优点

1. **刚需定位**：Token 压缩是 Agent 工程中的真实刚需，不是伪需求。每个重度 Agent 用户都能感受到上下文膨胀的痛苦。
2. **可逆压缩设计**：CCR 架构是真正的差异化创新，解决了"压缩 = 信息丢失"的根本顾虑。
3. **零侵入集成**：四种模式（Library/Proxy/Wrap/MCP）覆盖了几乎所有的接入场景，特别是 Proxy 模式对已有系统完全透明。
4. **结构感知压缩**：不是简单截断，而是按内容类型智能路由，JSON 用 SmartCrusher、代码用 AST、文本用 ML 模型——压缩质量远超粗暴截断。
5. **跨 Agent 共享记忆**：对于多 Agent 协作团队是杀手级功能。
6. **自我进化**：`headroom learn` 让 Agent 从失败中自动积累经验，是独特且有价值的特性。
7. **本地优先、隐私安全**：所有压缩计算本地完成，数据不离开本机。

#### 不足

1. **ML 模型依赖**：Kompress-base 需要 torch/transformers，安装体积较大（1-2GB），对于轻量场景可能过重。
2. **学习曲线**：配置项较多（CacheAligner、SmartCrusher、CCR 等），新手需要一定时间理解。
3. **压缩开销**：每次压缩增加约 5-10ms 延迟，对实时性要求极高的场景需注意。
4. **社区较新**：相比 LangChain 等成熟项目，社区和生态还在早期阶段。
5. **Python 3.10+ 限制**：不支持 Python 3.9 及以下版本。

#### 建议

1. **强烈推荐尝试**：如果你的团队在用 AI Agent（尤其是 Claude Code / Cursor / Codex），Token 成本是真实痛点，Headroom 是目前最完善的解决方案。
2. **从 Proxy 模式起步**：零代码改动，风险最低。先跑两周看实际效果，再决定是否深入。
3. **关注 CCR 可逆性**：如果你的场景对信息完整性有严格要求，CCR 是关键卖点——压缩不是截断，原文随时可取回。
4. **企业级场景**：建议 Docker 部署 + Proxy 模式，对已有系统完全透明，渐进式落地。
5. **性能基线**：先用 `headroom perf` 跑一下你自己的工作负载基线，实测压缩率再决定是否全面采用。
