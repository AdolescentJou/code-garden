# 0x1 查询引擎与对话循环——Claude Code 的心脏

> *系列：Claude Code 源码深度研究 · 专题 01 *
> *版本：v2.1.88 · 文件：*`*src/query.ts*`* · *`*src/QueryEngine.ts*`* · *`*src/services/api/claude.ts*`

---

### 一、从一次对话说起

你在终端输入一行提示词，按下回车。接下来发生了什么？

表面上看，Claude Code 把你的话发给 API，等待回复，然后执行工具，再把结果发回去——循环往复，直到任务完成。

但真实的实现远比这复杂。这篇文章要带你深入 Claude Code 的"心脏"：**查询引擎（QueryEngine）与对话循环（queryLoop）**，看清楚每一次对话背后的完整机制。

---

### 二、整体架构：三层嵌套的 AsyncGenerator

Claude Code 的查询链是三层嵌套的 AsyncGenerator，每一层都有明确的职责：

```TypeScript
┌─────────────────────────────────────────────────────────────┐
│  QueryEngine.submitMessage()                                 │
│  职责：会话状态管理、消息持久化、SDK 消息格式化、预算控制      │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  query() / queryLoop()   [src/query.ts]               │  │
│  │  职责：对话循环状态机、工具调度、压缩触发、错误恢复      │  │
│  │                                                       │  │
│  │  ┌─────────────────────────────────────────────────┐  │  │
│  │  │  queryModelWithStreaming()  [claude.ts]          │  │  │
│  │  │  职责：HTTP 流式请求、SSE 解析、重试、降级        │  │  │
│  │  └─────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

这三层都是 `AsyncGenerator`，用 `yield*` 串联，消息从最内层一路冒泡到最外层。这个设计让流式输出天然地穿透所有层次，不需要任何缓冲。

### 三、第一层：queryLoop——带状态机的 while(true)

`src/query.ts` 的核心是 `queryLoop` 函数，它是一个 `while(true)` 的 AsyncGenerator。

#### 3.1 State 结构体：对话的"快照"

每次循环迭代，queryLoop 都持有一个 `State` 对象：

```TypeScript
// src/query.ts（概念性简化，非原文）
type State = {
  messages: Message[]           // 当前对话历史
  systemPrompt: SystemPrompt    // 系统提示词
  userContext: string           // 用户上下文
  systemContext: string         // 系统上下文
  shouldCompact: boolean        // 是否需要压缩
  compactReason: CompactReason  // 压缩原因
  // ...
}
```

**关键设计**：State 在每个"continue 点"被**整体替换**，而不是局部修改。这意味着每次循环开始时，你拿到的是一个全新的快照，不存在部分更新导致的状态不一致问题。

#### 3.2 循环的骨架

```TypeScript
while (true) {
  ┌─ 1. 检查是否需要压缩（context 太长？）
  │     → 是：触发 reactive compact，替换 State，continue
  │
  ├─ 2. 调用 queryModelWithStreaming()，逐条消费流式消息
  │     → 遇到 tool_use：并发执行工具，收集结果
  │     → 遇到 end_turn：退出循环
  │     → 遇到 max_tokens：触发 max_output_tokens 恢复
  │
  ├─ 3. 处理工具结果，构造新的 user message
  │
  ├─ 4. 执行 stop hooks（如果有）
  │
  └─ 5. 更新 State，进入下一轮
```

#### 3.3 三种恢复路径

当对话遇到问题时，queryLoop 有三条恢复路径：

**路径一：Reactive Compact（上下文过长）**

```TypeScript
检测到 context 接近上限
    ↓
触发 compact（调用 Haiku 生成摘要）
    ↓
用摘要替换历史消息
    ↓
State 整体替换，continue 重新开始本轮
```

源码中的触发条件（`src/query/tokenBudget.ts`）：

```TypeScript
// 当 input tokens 超过模型上下文窗口的某个比例时触发
export function shouldCompact(usage: Usage, model: string): boolean {
  const contextWindow = getModelContextWindow(model)
  const usedTokens = usage.input_tokens + usage.cache_read_input_tokens
  return usedTokens > contextWindow * COMPACT_THRESHOLD_RATIO
}
```

**路径二：Context Collapse（极端情况）**

当 compact 之后上下文仍然太长（比如单条消息就超过了上下文窗口），会触发更激进的 context collapse：直接丢弃所有历史，只保留系统提示词和当前用户消息。

**路径三：max_output_tokens 恢复**

当 API 返回 `stop_reason: "max_tokens"` 时，说明模型的回复被截断了。queryLoop 会：

1. 注入一条特殊的 user message，告诉模型"你的回复被截断了，请继续"
2. 重新发起请求，让模型从截断处继续

这个机制让 Claude Code 能处理超长的代码生成任务，即使单次回复超过了 token 上限。

#### 3.4 工具并发调度

当模型返回多个 `tool_use` 块时，queryLoop 会并发执行它们：

```TypeScript
assistant message: [tool_use_1, tool_use_2, tool_use_3]
                         ↓
              Promise.all([exec(1), exec(2), exec(3)])
                         ↓
              user message: [tool_result_1, tool_result_2, tool_result_3]
```

但并发不是无限制的。权限系统会介入：需要用户确认的工具会暂停，等待用户响应后再继续。

#### 3.5 Stop Hooks

`src/query/stopHooks.ts` 实现了一个有趣的机制：在每轮对话结束后，可以注入额外的"检查"。

```TypeScript
// 概念性示意
async function* handleStopHooks(state: State, context: ToolUseContext) {
  for (const hook of getStopHooks()) {
    const result = await hook.check(state)
    if (result.shouldContinue) {
      // 注入新的 user message，触发下一轮对话
      yield* continueWithMessage(result.message, state, context)
    }
  }
}
```

Stop hooks 用于实现"自动验证"类功能：比如在代码修改后自动运行测试，如果测试失败则继续对话让模型修复。

### 四、第二层：QueryEngine——会话的"管家"

`src/QueryEngine.ts` 的 `QueryEngine` 类是对 `query.ts` 的封装，负责：

1. **消息持久化**：每次收到 assistant/user 消息，立即写入磁盘（`recordTranscript`）
2. **SDK 消息格式化**：把内部消息格式转换为 SDK 消费者期望的格式
3. **预算控制**：监控 USD 花费和 turn 数量，超限时提前终止
4. **会话恢复**：从磁盘加载历史消息，支持断点续传

#### 4.1 submitMessage() 的两条路径

`submitMessage()` 有两条执行路径，取决于是否是"重放"模式：

```TypeScript
submitMessage(prompt)
    │
    ├─ [重放模式] 直接 yield 历史消息，不调用 query()
    │   用于：会话恢复时重放已有对话
    │
    └─ [正常模式] 调用 query()，消费流式消息
        ├─ 每条 assistant 消息：fire-and-forget 写磁盘
        ├─ 每条 user 消息：await 写磁盘（确保顺序）
        └─ 最终 yield result 消息
```

#### 4.2 消息持久化的微妙之处

源码注释揭示了一个有趣的细节：

```TypeScript
// Fire-and-forget for assistant messages. claude.ts yields one
// assistant message per content block, then mutates the last
// one's message.usage/stop_reason on message_delta — relying on
// the write queue's 100ms lazy jsonStringify. Awaiting here
// blocks ask()'s generator, so message_delta can't run until
// every block is consumed; the drain timer (started at block 1)
// elapses first.
if (message.type === 'assistant') {
  void recordTranscript(messages)  // fire-and-forget
} else {
  await recordTranscript(messages) // await
}
```

为什么 assistant 消息用 fire-and-forget？因为 `claude.ts` 在 `content_block_stop` 时 yield 消息，但此时 `usage` 和 `stop_reason` 还是 null——真实值要等 `message_delta` 事件才到。写队列有 100ms 的懒序列化窗口，在这个窗口内 `message_delta` 会直接 mutate 已 yield 的消息对象，所以最终写入磁盘的是完整数据。

如果改成 await，就会阻塞 generator，导致 `message_delta` 无法执行，写入的永远是不完整的数据。

#### 4.3 结果类型

`submitMessage()` 最终 yield 一个 `result` 消息，有以下几种 subtype：

| subtype | 含义 |
| --- | --- |
| `success` | 正常完成 |
| `error_max_turns` | 超过最大 turn 数 |
| `error_max_budget_usd` | 超过 USD 预算 |
| `error_during_execution` | 执行过程中出错 |
| `error_max_structured_output_retries` | 结构化输出重试超限 |

### 五、第三层：queryModelWithStreaming——与 API 的直接对话

`src/services/api/claude.ts` 的 `queryModelWithStreaming` 是最底层，直接与 Anthropic API 交互。

#### 5.1 流式解析状态机

SSE 流的解析是一个状态机，核心数据结构是 `contentBlocks` 数组：

```TypeScript
message_start
    → 初始化 partialMessage，记录 ttftMs（首字节时间）

content_block_start (index=N, type=tool_use)
    → contentBlocks[N] = { ...block, input: '' }  // input 初始化为空字符串

content_block_delta (index=N, type=input_json_delta)
    → contentBlocks[N].input += delta.partial_json  // 累积 JSON 片段

content_block_stop (index=N)
    → 构造完整的 AssistantMessage，yield 出去

message_delta
    → 直接 mutate 最后一条 AssistantMessage 的 usage 和 stop_reason
    → 计算 USD 成本

message_stop
    → 流结束
```

**关键优化**：源码注释说明了为什么不用 `BetaMessageStream`：

```TypeScript
// Use raw stream instead of BetaMessageStream to avoid O(n²) partial JSON parsing
// BetaMessageStream calls partialParse() on every input_json_delta, which we don't need
// since we handle tool input accumulation ourselves
```

`BetaMessageStream` 每收到一个 `input_json_delta` 就尝试解析整个 JSON，复杂度是 O(n²)。Claude Code 自己管理累积，只在 `content_block_stop` 时解析一次，是 O(n)。

#### 5.2 流式降级机制

当流式请求失败时，有两级降级：

```TypeScript
流式请求失败
    │
    ├─ [用户主动中断 ESC] → 直接 throw APIUserAbortError，不降级
    │
    ├─ [SDK 超时] → 转换为 APIConnectionTimeoutError，进入降级
    │
    ├─ [流空闲超时 90s] → streamIdleAborted=true，进入降级
    │
    └─ [其他错误] → 降级到 executeNonStreamingRequest()
                        ↓
                   非流式请求（max_tokens 上限 64k）
                        ↓
                   如果也失败 → yield 错误消息，return
```

非流式降级的 token 上限是 64,000（`MAX_NON_STREAMING_TOKENS`），因为非流式 API 有 10 分钟超时限制。

#### 5.3 流式空闲超时看门狗

这是一个精心设计的防挂死机制：

```TypeScript
// 90 秒无数据 → 主动 abort 流
const STREAM_IDLE_TIMEOUT_MS = 90_000
// 45 秒无数据 → 打印警告日志
const STREAM_IDLE_WARNING_MS = STREAM_IDLE_TIMEOUT_MS / 2

// 每收到一个 chunk，重置计时器
for await (const part of stream) {
  resetStreamIdleTimer()  // 重置
  // ... 处理 part
}
```

没有这个机制，一个静默断开的连接会让 Claude Code 永远挂在那里，因为 SDK 的超时只覆盖初始 `fetch()`，不覆盖流式 body 的读取。

#### 5.4 paramsFromContext：请求参数的组装

每次 API 调用前，`paramsFromContext` 函数负责组装完整的请求参数。这个函数是一个闭包，捕获了整个请求上下文：

```TypeScript
paramsFromContext(retryContext) → {
  model,
  messages: addCacheBreakpoints(...),  // 添加 prompt cache 标记
  system: buildSystemPromptBlocks(...), // 系统提示词分块
  tools: allTools,
  betas: [...],                         // 动态 beta headers
  max_tokens,
  thinking,                             // extended thinking 配置
  temperature,                          // thinking 开启时不传
  context_management,                   // API 侧上下文管理
  speed,                                // fast mode
  output_config: { effort },            // effort 参数
}
```

**Beta headers 的 latch 机制**：某些 beta header（如 fast mode、AFK mode、cache editing）一旦在会话中启用，就会被"锁定"（latched），后续所有请求都带上这个 header。这是为了保证 prompt cache 的稳定性——cache key 包含 headers，如果 headers 变化，缓存就会失效。

### 六、withRetry：重试的艺术

`src/services/api/withRetry.ts` 实现了一套精密的重试逻辑。

#### 6.1 重试策略

```TypeScript
第1次失败 → 等待 base_delay * 2^0 + jitter
第2次失败 → 等待 base_delay * 2^1 + jitter
第3次失败 → 等待 base_delay * 2^2 + jitter
...
最大等待时间上限：60 秒
```

不同错误类型的处理：

| 错误类型 | 处理方式 |
| --- | --- |
| 429 Rate Limit | 读取 `retry-after` header，等待指定时间 |
| 529 Overloaded | 计入连续 529 计数器，超过阈值触发模型降级 |
| 401/403 Auth | 不重试，直接失败 |
| 404 | 不重试（但 claude.ts 会捕获并降级到非流式） |
| 网络超时 | 重试 |

#### 6.2 模型降级（FallbackTriggeredError）

当连续遇到 529 错误超过阈值时，withRetry 会抛出 `FallbackTriggeredError`，携带 fallback model 信息。这个错误会一路冒泡到 `query.ts`，在那里执行实际的模型切换，然后用新模型重新发起请求。

```TypeScript
withRetry 检测到连续 529 超过阈值
    ↓
throw FallbackTriggeredError { fallbackModel: 'claude-3-5-haiku-...' }
    ↓
claude.ts catch → re-throw（不处理）
    ↓
query.ts catch → 切换 model，重新调用 queryModelWithStreaming
```

#### 6.3 Persistent Retry 模式

对于某些特殊场景（如 SDK 模式），withRetry 支持"持久重试"：不限制重试次数，一直重试直到成功或用户中断。这用于处理长时间运行的 agentic 任务中的临时网络问题。

### 七、Prompt Caching：省钱的关键

Claude Code 对 prompt caching 有精心的设计。

#### 7.1 Cache Breakpoint 策略

`addCacheBreakpoints` 函数在消息列表中插入 `cache_control` 标记：

```TypeScript
messages: [msg_0, msg_1, msg_2, msg_3(最新)]
                                    ↑
                              cache_control: { type: 'ephemeral' }
```

**只在最后一条消息上打标记**。原因是 Anthropic 的 KV cache 服务器（Mycro）会在每个 cache 位置保护其之前的 KV pages。如果打两个标记，倒数第二个位置的 KV pages 会被多保留一轮，浪费内存。

#### 7.2 系统提示词的分块缓存

系统提示词被分成多个块，每块可以有不同的 cache scope：

```TypeScript
// src/services/api/claude.ts
export function buildSystemPromptBlocks(
  systemPrompt: SystemPrompt,
  enablePromptCaching: boolean,
): TextBlockParam[] {
  return splitSysPromptPrefix(systemPrompt).map(block => ({
    type: 'text',
    text: block.text,
    ...(enablePromptCaching && block.cacheScope !== null && {
      cache_control: getCacheControl({ scope: block.cacheScope }),
    }),
  }))
}
```

系统提示词的前缀（工具定义、核心指令）变化频率低，适合长期缓存；用户上下文（当前目录、文件列表）变化频率高，用短期缓存或不缓存。

### 八、完整数据流图

一次完整的对话轮次，数据流如下：

```TypeScript
用户输入
    │
    ▼
QueryEngine.submitMessage()
    │  构造 UserMessage，加入 mutableMessages
    │
    ▼
query() / queryLoop()
    │  检查是否需要 compact
    │  准备 systemPrompt、userContext
    │
    ▼
queryModelWithStreaming()
    │  paramsFromContext() 组装请求参数
    │  withRetry() 管理重试
    │
    ▼
Anthropic API (SSE 流)
    │
    ▼  ← message_start
    │  ← content_block_start (text)
    │  ← content_block_delta (text_delta) × N
    │  ← content_block_stop
    │  ← content_block_start (tool_use)
    │  ← content_block_delta (input_json_delta) × M
    │  ← content_block_stop
    │  ← message_delta (usage, stop_reason)
    │  ← message_stop
    │
    ▼
AssistantMessage (yield 给上层)
    │
    ▼
queryLoop 检测到 tool_use
    │  并发执行工具
    │  构造 UserMessage (tool_results)
    │
    ▼
下一轮 queryModelWithStreaming()
    │
    ▼
... (循环直到 end_turn)
    │
    ▼
QueryEngine 收到最终 assistant message
    │  写磁盘，yield result 消息
    │
    ▼
调用方（REPL / SDK）
```

### 九、设计哲学总结

通读这三个文件，可以提炼出几个核心设计哲学：

**1. AsyncGenerator 作为统一的流式抽象**

整个调用链都是 AsyncGenerator，用 `yield*` 串联。这让流式输出天然穿透所有层次，不需要任何缓冲或回调地狱。

**2. 状态整体替换，而非局部修改**

queryLoop 的 State 在每个 continue 点整体替换。这避免了复杂的状态同步问题，让每次循环都从一个干净的快照开始。

**3. 错误恢复是一等公民**

三种 compact 路径、流式降级、模型降级、max_tokens 恢复——每一种异常情况都有明确的处理路径，而不是简单地抛出错误。

**4. 性能细节无处不在**

- 避免 O(n²) 的 JSON 解析
- fire-and-forget 写磁盘（利用 100ms 懒序列化窗口）
- 单个 cache breakpoint（避免 KV pages 泄漏）
- 流式空闲超时看门狗（防止永久挂死）

**5. 可观测性内嵌于核心路径**

`queryCheckpoint`、`logEvent`、`logAPIQuery` 散布在关键路径上，每个重要的时间点都有记录。这不是事后加的，而是设计时就考虑进去的。

### 十、给 mini-claude-code 的启示

如果要复刻一个最小可运行版本，查询引擎这部分的核心骨架是：

```TypeScript
async function* queryLoop(messages, systemPrompt, tools) {
  while (true) {
    // 1. 调用 API
    const response = await callAPI(messages, systemPrompt, tools)
    
    // 2. 检查 stop_reason
    if (response.stop_reason === 'end_turn') {
      yield response
      return
    }
    
    if (response.stop_reason === 'tool_use') {
      // 3. 执行工具
      const toolResults = await Promise.all(
        response.tool_uses.map(t => executeTool(t))
      )
      
      // 4. 构造新的 user message
      messages.push(response)
      messages.push({ role: 'user', content: toolResults })
      
      // 5. 继续循环
      continue
    }
  }
}
```

这个骨架只有 20 行，但已经包含了 queryLoop 的核心逻辑。真实实现在这个骨架上叠加了：compact、错误恢复、权限检查、持久化、流式处理、重试……每一层都是为了解决真实世界中遇到的具体问题。
