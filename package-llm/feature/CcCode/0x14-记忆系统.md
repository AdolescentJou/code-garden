### 一、从一次"失忆"说起

你上周花了两小时给 Claude Code 解释项目架构，它帮你做了很多决策。今天重新打开，它什么都不记得了——你得从头再说一遍。

表面上看，这是大语言模型的根本局限，上下文窗口有限，会话结束就清空——没办法吧？

但 Claude Code 并没有接受这个限制。它用三个相互协作的子系统来对抗遗忘：会话中实时提取记忆、会话结束后异步整合、用 AI 理解语义而不是用规则匹配关键词。这套系统让 Claude Code 能在多次会话之间保持对你和你项目的持续认知。

这篇文章要带你深入 `src/services/SessionMemory/`、`src/services/autoDream/`、`src/services/extractMemories/`，看清楚这套记忆系统的完整设计。

Claude Code 用三个相互协作的子系统来对抗这个问题：

**SessionMemory**：在当前会话进行中，后台悄悄提取"会话笔记"，写入 markdown 文件，供下次会话读取。

**AutoDream**：在会话结束后（或满足触发条件时），把多个会话的笔记整合成更高层次的"长期记忆"。

**extractMemories**：被 SessionMemory 和 AutoDream 调用的底层能力，用 AI 自身来提取和整理记忆。

三个系统形成了一个完整的记忆生命周期：**实时提取 → 会话存储 → 跨会话整合**。

> 交叉引用：SessionMemory 和 extractMemories 使用 `forkAgent` 创建子 Agent（→ 参见**专题 09**：多 Agent 系统），AutoDream 的触发可以通过 Hooks 系统配置（→ 参见**专题 10**：Hooks 系统），长期记忆在启动流程中被注入系统提示词（→ 参见**专题 12**：启动流程）。

### 二、SessionMemory：实时的会话笔记员

`sessionMemory.ts` 解决的问题是：**如何在不打断当前对话的情况下，持续提取有价值的信息？**

#### 2.1 后台 Forked Agent

核心设计是**在后台 fork 一个独立的 AI agent**，专门负责提取笔记，完全不影响主对话流程：

```TypeScript
// 代码块
export async function extractSessionNotes(
  conversationHistory: Message[],
  projectRoot: string,
): Promise<void> {
  // 不在主线程运行，而是 fork 一个独立 agent
  const agent = await forkAgent({
    systemPrompt: SESSION_NOTES_SYSTEM_PROMPT,
    messages: [
      {
        role: 'user',
        content: buildExtractionPrompt(conversationHistory),
      },
    ],
    // 关键限制：这个 agent 只能使用文件写入工具
    allowedTools: ['write_file'],
    maxTokens: 2048,
  })

  await agent.run()
}

```

`forkAgent` 创建了一个完全独立的 AI 实例，它有自己的上下文窗口，不会污染主对话的状态。这个设计的优雅之处在于：**用 AI 来理解 AI 的对话**，而不是用规则引擎来解析。

#### 2.2 触发时机

SessionMemory 不是每轮对话都触发，而是有节流机制：

```TypeScript
// 代码块
const EXTRACTION_INTERVAL = 10 // 每 10 轮对话触发一次
const MIN_MESSAGES_FOR_EXTRACTION = 5 // 至少 5 条消息才触发

export function shouldExtractNotes(
  messageCount: number,
  lastExtractionAt: number,
): boolean {
  if (messageCount < MIN_MESSAGES_FOR_EXTRACTION) return false
  if (messageCount % EXTRACTION_INTERVAL !== 0) return false
  return true
}

```

每 10 轮对话触发一次，且至少需要 5 条消息。这个设计避免了在对话刚开始时就触发提取（此时信息量太少，提取没有意义），也避免了过于频繁的提取（每轮都提取会显著增加 API 调用成本）。

#### 2.3 提取提示词

系统提示词是 SessionMemory 的灵魂：

```TypeScript
// 代码块
const SESSION_NOTES_SYSTEM_PROMPT = `
You are a note-taking assistant. Your job is to extract important information
from a conversation between a user and Claude Code.

Extract and save notes about:
- Technical decisions made (e.g., "decided to use PostgreSQL instead of MySQL")
- Problems encountered and their solutions
- User preferences and coding style
- Project-specific context (architecture, conventions, constraints)
- TODO items or follow-up tasks mentioned

Do NOT include:
- Routine back-and-forth conversation
- Information that is already in the codebase
- Temporary debugging steps that were resolved

Write the notes in a concise, structured format to a file called session-notes.md
in the project root. If the file already exists, UPDATE it rather than replacing it.
`

```

这个提示词的设计非常精准。它明确告诉 AI"要提取什么"和"不要提取什么"，避免了笔记文件被无用信息淹没。特别是"如果文件已存在，更新而非替换"——这确保了跨多次提取的信息积累，而不是每次都从头开始。

#### 2.4 写入策略

```TypeScript
// 代码块
async function writeSessionNotes(
  notes: string,
  projectRoot: string,
): Promise<void> {
  const notesPath = path.join(projectRoot, 'session-notes.md')

  // 读取现有笔记
  let existing = ''
  try {
    existing = await fs.readFile(notesPath, 'utf-8')
  } catch {
    // 文件不存在，从空开始
  }

  // 合并：新笔记追加到现有笔记后面，带时间戳
  const timestamp = new Date().toISOString()
  const merged = existing
    ? `${existing}\n\n---\n*Updated: ${timestamp}*\n\n${notes}`
    : `*Created: ${timestamp}*\n\n${notes}`

  await fs.writeFile(notesPath, merged, 'utf-8')
}

```

时间戳的设计很有意思——它让 AutoDream 在整合时可以判断信息的新鲜度，优先保留最近的笔记。

### 三、AutoDream：跨会话的记忆整合器

如果说 SessionMemory 是"速记员"，那 AutoDream 就是"整理员"——它定期把散乱的会话笔记整合成结构化的长期记忆。

名字"AutoDream"来自一个有趣的类比：人类在睡眠中整合白天的记忆，形成长期记忆。AutoDream 做的是类似的事情——在"空闲时间"（会话间隙）整合短期记忆。

#### 3.1 三重门控

AutoDream 的触发有三个独立的门控条件，**必须同时满足**：

```TypeScript
// 代码块
interface AutoDreamTriggerConditions {
  timeSinceLastDream: number    // 距上次整合的时间（毫秒）
  sessionsSinceLastDream: number // 距上次整合的会话数
  hasNewSessionNotes: boolean   // 是否有新的会话笔记
}

const DREAM_INTERVAL_MS = 24 * 60 * 60 * 1000  // 24 小时
const MIN_SESSIONS_FOR_DREAM = 5                 // 至少 5 个新会话

export function shouldTriggerDream(
  conditions: AutoDreamTriggerConditions,
): boolean {
  // 三个条件必须同时满足
  return (
    conditions.timeSinceLastDream >= DREAM_INTERVAL_MS &&
    conditions.sessionsSinceLastDream >= MIN_SESSIONS_FOR_DREAM &&
    conditions.hasNewSessionNotes
  )
}

```

**时间门控（24h）**：防止在短时间内反复整合，浪费 API 调用。

**会话数门控（5个）**：确保有足够的新信息值得整合。如果你只开了一个新会话，没必要重新整合所有记忆。

**内容门控**：如果没有新的会话笔记，整合没有意义。

这三重门控的组合非常精妙——它在"及时更新记忆"和"避免过度消耗"之间找到了平衡。

#### 3.2 文件锁：防止并发整合

AutoDream 的一个关键工程细节是**文件锁**。如果用户同时打开了多个 Claude Code 窗口，可能会有多个 AutoDream 实例同时尝试整合记忆，导致数据竞争：

```TypeScript
// 代码块
const LOCK_FILE = '.autodream.lock'
const LOCK_TIMEOUT_MS = 60_000 // 60 秒后锁自动过期

async function acquireLock(projectRoot: string): Promise<boolean> {
  const lockPath = path.join(projectRoot, LOCK_FILE)

  try {
    // 检查锁是否已存在且未过期
    const stat = await fs.stat(lockPath)
    const lockAge = Date.now() - stat.mtimeMs
    if (lockAge < LOCK_TIMEOUT_MS) {
      return false // 锁被其他进程持有
    }
    // 锁已过期，可以覆盖
  } catch {
    // 锁文件不存在，可以创建
  }

  // 写入锁文件（包含当前进程 ID）
  await fs.writeFile(lockPath, String(process.pid), 'utf-8')
  return true
}

async function releaseLock(projectRoot: string): Promise<void> {
  const lockPath = path.join(projectRoot, LOCK_FILE)
  await fs.unlink(lockPath).catch(() => {}) // 忽略删除失败
}

```

60 秒的锁超时是一个安全网——如果持有锁的进程崩溃，锁不会永久阻塞其他进程。这是分布式系统中"租约"（lease）模式的简化版本。

#### 3.3 整合流程

```TypeScript
// 代码块
export async function runAutoDream(projectRoot: string): Promise<void> {
  // 1. 检查触发条件
  const conditions = await checkTriggerConditions(projectRoot)
  if (!shouldTriggerDream(conditions)) return

  // 2. 获取文件锁
  const locked = await acquireLock(projectRoot)
  if (!locked) return // 其他进程正在整合

  try {
    // 3. 读取所有会话笔记
    const sessionNotes = await readAllSessionNotes(projectRoot)
    if (sessionNotes.length === 0) return

    // 4. 读取现有长期记忆
    const existingMemory = await readLongTermMemory(projectRoot)

    // 5. 调用 extractMemories 整合
    const newMemory = await extractMemories({
      sessionNotes,
      existingMemory,
      projectRoot,
    })

    // 6. 写入长期记忆文件
    await writeLongTermMemory(projectRoot, newMemory)

    // 7. 归档已处理的会话笔记
    await archiveSessionNotes(projectRoot)

    // 8. 更新最后整合时间
    await updateLastDreamTime(projectRoot)

  } finally {
    // 无论成功失败，都释放锁
    await releaseLock(projectRoot)
  }
}

```

`try...finally` 确保了锁一定会被释放，即使整合过程中发生异常。这是 RAII（资源获取即初始化）模式在异步 JavaScript 中的体现。

#### 3.4 会话笔记的归档

整合完成后，已处理的会话笔记不会被删除，而是被**归档**：

```TypeScript
// 代码块
async function archiveSessionNotes(projectRoot: string): Promise<void> {
  const notesPath = path.join(projectRoot, 'session-notes.md')
  const archiveDir = path.join(projectRoot, '.claude', 'memory-archive')
  const timestamp = new Date().toISOString().replace(/[:.]/g, '-')
  const archivePath = path.join(archiveDir, `session-notes-${timestamp}.md`)

  await fs.mkdir(archiveDir, { recursive: true })
  await fs.rename(notesPath, archivePath)
}

```

归档而非删除，保留了完整的历史记录。这对调试很有价值——如果 AutoDream 的整合结果不理想，可以查看原始会话笔记，理解整合过程中发生了什么。

### 四、extractMemories：用 AI 整理 AI 的记忆

`extractMemories.ts` 是记忆系统的核心算法层。它的任务是：**给定一堆会话笔记和现有的长期记忆，生成一份更好的长期记忆**。

#### 4.1 整合提示词

```TypeScript
// 代码块
const MEMORY_CONSOLIDATION_PROMPT = `
You are a memory consolidation assistant. You will be given:
1. Existing long-term memory about a software project
2. New session notes from recent conversations

Your task is to create an updated, consolidated memory that:
- Merges new information with existing memory
- Removes outdated or superseded information
- Resolves contradictions (prefer newer information)
- Organizes information into clear categories:
  * Project Overview (architecture, tech stack, key decisions)
  * User Preferences (coding style, workflow preferences)
  * Known Issues & Solutions (bugs encountered and fixed)
  * Ongoing Work (current tasks, next steps)
  * Important Context (constraints, external dependencies)

Keep the output concise. Aim for 500-1000 words.
Remove information that is no longer relevant or has been resolved.
`

```

这个提示词的设计有几个值得注意的地方：

**矛盾解决策略**：明确指定"优先使用更新的信息"。这处理了一个常见场景——你上周决定用 MySQL，这周改成了 PostgreSQL，记忆应该反映最新决定。

**信息分类**：五个固定类别（项目概览、用户偏好、已知问题、进行中的工作、重要上下文）让记忆结构化，便于下次会话快速定位相关信息。

**长度控制**：500-1000 词的目标长度，确保记忆文件不会无限膨胀。

#### 4.2 canUseTool 限制

`extractMemories` 有一个重要的安全限制：

```TypeScript
// 代码块
export async function extractMemories(params: ExtractMemoriesParams): Promise<string> {
  const agent = await forkAgent({
    systemPrompt: MEMORY_CONSOLIDATION_PROMPT,
    messages: buildConsolidationMessages(params),
    // 严格限制：只能读文件和写文件，不能执行命令
    canUseTool: (toolName: string) => {
      return ['read_file', 'write_file'].includes(toolName)
    },
    maxTokens: 4096,
  })

  const result = await agent.run()
  return result.finalOutput
}

```

`canUseTool` 是一个白名单函数，只允许 `read_file` 和 `write_file`。这个限制至关重要——记忆整合 agent 不应该有权限执行 bash 命令、调用网络接口或修改代码。它只是一个"读写文件的整理员"，不是一个"能做任何事的 agent"。

这体现了**最小权限原则**：每个 agent 只获得完成其任务所必需的最小权限集合。

#### 4.3 增量整合 vs 全量重写

```TypeScript
// 代码块
function buildConsolidationMessages(params: ExtractMemoriesParams): Message[] {
  const { sessionNotes, existingMemory } = params

  const userMessage = existingMemory
    ? `
## Existing Long-term Memory
${existingMemory}

## New Session Notes to Integrate
${sessionNotes.join('\n\n---\n\n')}

Please update the long-term memory by integrating the new session notes.
`
    : `
## Session Notes
${sessionNotes.join('\n\n---\n\n')}

Please create a long-term memory summary from these session notes.
`

  return [{ role: 'user', content: userMessage }]
}

```

当存在现有长期记忆时，是**增量整合**（在现有基础上更新）；当没有时，是**全量创建**（从会话笔记从头生成）。这个区分很重要——增量整合保留了历史积累的知识，而不是每次都从零开始。

三个系统共同维护了一套文件结构：

```TypeScript

├── .claude/
```

### 六、记忆的注入：如何让新会话"记得"

记忆文件写好了，但如何让新会话读取它？这发生在会话启动阶段：

```TypeScript
// 代码块
// 在 startup 流程中（src/startup.ts）
async function loadProjectMemory(projectRoot: string): Promise<string | null> {
  const memoryPath = path.join(projectRoot, '.claude', 'long-term-memory.md')

  try {
    const memory = await fs.readFile(memoryPath, 'utf-8')
    if (memory.trim().length === 0) return null
    return memory
  } catch {
    return null // 文件不存在，正常情况
  }
}

// 注入到系统提示词
function buildSystemPrompt(projectMemory: string | null): string {
  const basePrompt = BASE_SYSTEM_PROMPT

  if (!projectMemory) return basePrompt

  return `${basePrompt}

## Project Memory
The following is accumulated knowledge about this project from previous sessions:

${projectMemory}

Use this context to provide more relevant and consistent assistance.`
}

```

长期记忆被注入到**系统提示词**中，而不是用户消息中。这意味着它对 Claude 来说是"背景知识"，而不是"用户说的话"。这个区分在 Claude 的注意力机制中有实际影响——系统提示词的内容会被更稳定地"记住"。

### 七、工程亮点与设计哲学

#### 7.1 用 AI 理解 AI

最有趣的设计决策是：**用 AI 来提取和整合 AI 的对话记忆**。这不是用规则引擎解析对话，而是用另一个 AI 实例来理解语义。

这个选择的代价是 API 调用成本，但收益是极高的灵活性——AI 能理解"我们决定放弃这个方案"这样的隐含信息，而规则引擎做不到。

#### 7.2 三重门控的精妙平衡

AutoDream 的三重门控（时间 + 会话数 + 内容）是一个精心设计的节流机制。单一门控会有问题：只有时间门控，可能在没有新信息时浪费 API 调用；只有会话数门控，可能在短时间内触发太多次；只有内容门控，可能在每次会话后都触发。三重组合才能在各种使用模式下都表现良好。

#### 7.3 最小权限原则的贯彻

`extractMemories` 的 `canUseTool` 白名单是最小权限原则的直接体现。在 Claude Code 的多 agent 架构中，每个 agent 都有明确的权限边界。这不仅是安全考虑，也是工程上的"关注点分离"——记忆整合 agent 只做记忆整合，不做其他事情。

#### 7.4 归档而非删除

会话笔记在整合后被归档而非删除，这体现了"数据不可变"的设计哲学。在调试记忆系统时，能够查看原始会话笔记是非常有价值的。这也为未来的功能扩展留了余地——例如，可以实现"回滚到某个时间点的记忆状态"。

#### 7.5 优雅降级

整个记忆系统是**完全可选的**。如果 `long-term-memory.md` 不存在，Claude Code 正常工作，只是没有跨会话记忆。如果 AutoDream 触发失败（例如 API 调用超时），会话笔记仍然保留，下次会再次尝试整合。这种设计确保了记忆系统的故障不会影响核心功能。

### 八、局限性与潜在问题

#### 8.1 记忆的"幻觉"风险

用 AI 提取记忆，意味着提取过程本身可能产生幻觉。如果 AI 错误地"记住"了一个从未发生的决定，这个错误会被持久化到长期记忆中，影响未来的所有会话。

缓解措施：归档原始会话笔记，允许用户手动检查和修正记忆文件。

#### 8.2 记忆的过时问题

长期记忆可能包含过时信息。例如，记忆中说"使用 React 16"，但项目已经升级到 React 18。AutoDream 的整合提示词要求"删除过时信息"，但 AI 不一定能准确判断什么是"过时的"。

缓解措施：记忆文件是普通 markdown，用户可以直接编辑。

#### 8.3 多项目的记忆隔离

每个项目有独立的 `.claude/` 目录，记忆是**项目级别**的，不是用户级别的。这意味着你在项目 A 学到的"用户偏好 TypeScript 严格模式"不会自动应用到项目 B。

这是一个有意的设计选择——项目级别的记忆更精确，避免了跨项目的信息污染。但对于用户的通用偏好（例如"总是写注释"），需要在每个项目里重新建立记忆。

### 九、与其他系统的集成

**与 Startup 系统的集成**：会话启动时，startup 流程读取 `long-term-memory.md` 并注入系统提示词。这是记忆系统与主对话流程的唯一接触点。

**与 Multi-agent 系统的集成**：SessionMemory 和 extractMemories 都使用了 `forkAgent` 创建子 agent。这些子 agent 的生命周期由 Multi-agent 系统管理，包括超时控制、错误处理和资源清理。

**与 Hooks 系统的集成**：AutoDream 的触发可以通过 Hooks 系统配置。例如，可以设置一个 hook 在每次会话结束时强制触发 AutoDream，而不等待三重门控条件满足。

### 十、给 mini-claude-code 的启示

mini-claude-code 目前没有跨会话记忆，可以用最简单的方式实现核心功能：

```Python
// 代码块
# mini-claude-code 的极简记忆系统
# 对应 Claude Code 的 SessionMemory + AutoDream（简化版）

import json
from pathlib import Path
from datetime import datetime

MEMORY_FILE = ".claude/memory.md"

def load_memory(project_root: str) -> str:
    """
    读取长期记忆，注入系统提示词。
    对应 Claude Code 的 loadProjectMemory() + buildSystemPrompt()。
    """
    memory_path = Path(project_root) / MEMORY_FILE
    if not memory_path.exists():
        return ""
    content = memory_path.read_text().strip()
    if not content:
        return ""
    return f"\n\n## Project Memory\n{content}\n"

async def save_session_notes(conversation: list[dict], project_root: str):
    """
    会话结束时，用 AI 提取关键信息并追加到记忆文件。
    对应 Claude Code 的 extractSessionNotes()（简化版，非后台 fork）。
    """
    if len(conversation) < 5:  # 对话太短，不值得提取
        return

    # 构建提取 prompt
    history_text = "\n".join([
        f"{m['role'].upper()}: {m['content'][:500]}"
        for m in conversation[-20:]  # 只看最近 20 条
    ])

    extraction_prompt = f"""从以下对话中提取值得记住的信息（技术决策、用户偏好、项目上下文）。
用简洁的 Markdown 格式输出，不超过 200 字。如果没有值得记录的信息，输出"无"。

对话记录：
{history_text}"""

    response = await call_api([{"role": "user", "content": extraction_prompt}])
    notes = response.content[0].text.strip()

    if notes and notes != "无":
        memory_path = Path(project_root) / MEMORY_FILE
        memory_path.parent.mkdir(exist_ok=True)
        timestamp = datetime.now().strftime("%Y-%m-%d")
        existing = memory_path.read_text() if memory_path.exists() else ""
        memory_path.write_text(
            f"{existing}\n\n---\n*{timestamp}*\n\n{notes}".strip()
        )

```

**最值得从 Claude Code 借鉴的两个设计**：

第一，**三重门控（时间 + 会话数 + 内容）**。不要在每次会话结束时都触发记忆整合——这会浪费 API 调用。至少要有"对话足够长"和"距上次整合有足够时间"两个条件同时满足才触发。

第二，**记忆注入系统提示词而非用户消息**。长期记忆应该作为"背景知识"注入系统提示词，而不是作为"用户说的话"注入对话历史。这在 Claude 的注意力机制中有实际影响——系统提示词的内容会被更稳定地"记住"，不会被后续的对话内容覆盖。

### 结语

Claude Code 的记忆系统是一个优雅的工程解决方案，它用三个相互协作的子系统解决了 AI 的"遗忘症"问题：SessionMemory 实时提取，AutoDream 定期整合，extractMemories 提供 AI 驱动的语义理解。

这套系统最值得学习的不是技术细节，而是设计哲学：**用 AI 来增强 AI**。不是用规则引擎解析对话，而是用另一个 AI 实例来理解语义；不是用数据库存储结构化数据，而是用 markdown 文件存储自然语言记忆。这种"AI-native"的设计思路，可能是未来 AI 应用架构的重要方向。
