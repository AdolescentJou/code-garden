### 一、从一次权限提示说起

Claude Code 准备执行一条命令，终端弹出了确认框：「是否允许运行 `rm -rf ./dist`？」你按下了 y。

表面上看，Claude Code 遇到危险操作就问一下用户，用户说允许就执行——不就这样吗？

但真实的实现远比这复杂。权限决策要考虑当前是否开启了自动模式、用户是否预先配置了允许规则、操作是否涉及 `.git/hooks` 这类即使开了自动模式也必须询问的敏感路径、是否在无头模式下运行根本没有人可以回答。Claude Code 为此构建了一套五层的权限系统，每一层都有明确的职责边界。

这篇文章要带你深入这套权限系统，看清楚每一次「允许/拒绝」决策背后的完整逻辑。

整个权限系统可以分为五层：

```TypeScript
// 代码块
+------------------------------------------------------------------+
|                      权限模式层                                  |
|  PermissionMode：default / plan / acceptEdits / bypassPermissions|
|                  dontAsk / auto（内部）                          |
+------------------------------------------------------------------+
|                      规则引擎层                                  |
|  PermissionRule：allow / deny / ask 三种行为                     |
|  来源：userSettings / projectSettings / localSettings / cliArg  |
+------------------------------------------------------------------+
|                      决策流水线层                                |
|  hasPermissionsToUseToolInner：10个步骤的决策树                  |
+------------------------------------------------------------------+
|                      AI 分类器层（内部）                         |
|  yoloClassifier：Auto 模式下用 AI 判断操作是否安全               |
+------------------------------------------------------------------+
|                      安全兜底层                                  |
|  dangerousPatterns / denialTracking：防止规则被滥用              |
+------------------------------------------------------------------+

```

> 权限决策在工具执行流水线的第六阶段触发（→ 参见**专题 05**：工具系统）；Hooks 可以在 `PreToolUse` 阶段提供权限决策，绕过或增强默认权限逻辑（→ 参见**专题 10**：Hooks 系统）；启动流程中的信任对话框是权限系统的第一道门（→ 参见**专题 12**：启动流程）。

### 二、权限模式：六种运行状态

#### 2.1 模式定义

```TypeScript
// 代码块
// src/types/permissions.ts
export const PERMISSION_MODES = [
  'default',           // 默认：每次操作都询问用户
  'plan',              // 计划模式：只读，不执行写操作
  'acceptEdits',       // 接受编辑：自动允许文件编辑，其他操作仍询问
  'bypassPermissions', // 绕过权限：自动允许所有操作（危险！）
  'dontAsk',           // 不询问：将所有 ask 转为 deny
  'auto',              // 自动模式（内部/Ant 专用）：AI 分类器决策
  'bubble',            // 气泡模式（内部）
] as const

```

#### 2.2 模式的视觉标识

每种模式都有对应的 UI 标识，让用户一眼看出当前状态：

```TypeScript
// 代码块
const PERMISSION_MODE_CONFIG = {
  default:           { title: 'Default',            symbol: '',    color: 'text'      },
  plan:              { title: 'Plan Mode',           symbol: '⏸',  color: 'planMode'  },
  acceptEdits:       { title: 'Accept edits',        symbol: '⏵⏵', color: 'autoAccept'},
  bypassPermissions: { title: 'Bypass Permissions',  symbol: '⏵⏵', color: 'error'     },
  dontAsk:           { title: "Don't Ask",           symbol: '⏵⏵', color: 'error'     },
  auto:              { title: 'Auto mode',           symbol: '⏵⏵', color: 'warning'   },
}

```

注意 `bypassPermissions` 和 `dontAsk` 都用了 `error` 颜色——这是有意为之的警示设计。

#### 2.3 外部模式 vs 内部模式

`auto` 模式是 Ant（Anthropic 内部）专用的，外部用户无法使用：

```TypeScript
// 代码块
export function isExternalPermissionMode(mode: PermissionMode): boolean {
  if (process.env.USER_TYPE !== 'ant') {
    return true  // 外部用户的所有模式都是"外部模式"
  }
  return mode !== 'auto' && mode !== 'bubble'  // Ant 用户排除内部模式
}

```

### 三、权限规则：三种行为 × 多个来源

#### 3.1 规则结构

```TypeScript
// 代码块
type PermissionRule = {
  source: PermissionRuleSource    // 规则来自哪里
  ruleBehavior: PermissionBehavior // allow / deny / ask
  ruleValue: PermissionRuleValue  // 规则内容
}

type PermissionRuleValue = {
  toolName: string        // 工具名，如 "Bash"
  ruleContent?: string    // 可选内容，如 "npm publish:*"
}

```

#### 3.2 规则来源（优先级从高到低）

```TypeScript
// 代码块
policySettings   - 企业策略（只读，最高优先级）
flagSettings     - 功能标志（只读）
command          - 命令行参数（只读）
cliArg           - CLI 参数（内存中，不持久化）
session          - 会话级别（内存中，不持久化）
projectSettings  - 项目级别（.claude/settings.json）
localSettings    - 本地级别（.claude/settings.local.json）
userSettings     - 用户级别（~/.claude/settings.json）

```

#### 3.3 规则语法

规则字符串格式：`ToolName(content:pattern)`

```TypeScript

Bash(npm publish:*)     - 允许/拒绝以 "npm publish" 开头的命令

mcp__server1__*         - 通配符：允许/拒绝 server1 的所有工具

```

#### 3.4 规则的持久化


### 四、决策流水线：hasPermissionsToUseToolInner 的 10 个步骤

这是权限系统的核心函数，位于 `src/utils/permissions/permissions.ts`。它按优先级顺序检查各种条件，一旦有明确结论就立即返回：

```TypeScript
// 代码块
输入：tool + input + context
         |
         v
步骤1a: 工具是否在 deny 规则中？
         | YES -> return { behavior: 'deny', reason: 'rule' }
         | NO  |
               v
步骤1b: 工具是否在 ask 规则中？
         | YES（且不能沙箱自动允许）-> return { behavior: 'ask', reason: 'rule' }
         | NO  |
               v
步骤1c: 调用 tool.checkPermissions()
         | 获取 toolPermissionResult
         |
         v
步骤1d: toolPermissionResult.behavior === 'deny'？
         | YES -> return deny
         | NO  |
               v
步骤1e: tool.requiresUserInteraction() && result === 'ask'？
         | YES -> return ask（即使在 bypass 模式也要询问）
         | NO  |
               v
步骤1f: 内容特定的 ask 规则（如 Bash(npm publish:*)）？
         | YES -> return ask（bypass 模式也不能绕过）
         | NO  |
               v
步骤1g: 安全检查（.git/ .claude/ .vscode/ shell 配置）？
         | YES -> return ask（bypass 模式也不能绕过）
         | NO  |
               v
步骤2a: 是否应该绕过权限？
         | YES（bypassPermissions 或 plan+bypass 可用）-> return allow
         | NO  |
               v
步骤2b: 工具是否在 allow 规则中？
         | YES -> return allow
         | NO  |
               v
步骤3:  passthrough -> ask 转换
         | return { behavior: 'ask', message: ... }

```

#### 4.1 步骤1g：安全检查的特殊地位

安全检查（`safetyCheck`）是整个权限系统中最特殊的存在——它**不能被任何模式绕过**，包括 `bypassPermissions`：

```TypeScript
// 代码块
// 1g. Safety checks are bypass-immune
if (
  toolPermissionResult?.behavior === 'ask' &&
  toolPermissionResult.decisionReason?.type === 'safetyCheck'
) {
  return toolPermissionResult  // 直接返回，不检查 bypass 模式
}

```

哪些路径会触发安全检查？

```TypeScript
// 代码块
.git/           - Git 仓库元数据
.claude/        - Claude Code 配置
.vscode/        - VS Code 配置
~/.bashrc       - Shell 配置
~/.zshrc        - Shell 配置
~/.ssh/         - SSH 密钥

```

这些路径的修改可能导致严重的安全问题（如修改 `.git/hooks` 来植入恶意代码），因此即使用户开启了 `bypassPermissions` 模式，也必须手动确认。

#### 4.2 步骤1e：requiresUserInteraction 的特殊工具

某些工具天然需要用户交互，即使在自动模式下也不能跳过：

```TypeScript
// 代码块
// AskUserQuestionTool：需要用户回答问题
requiresUserInteraction: () => true

// ExitPlanModeTool：需要用户确认退出计划模式
requiresUserInteraction: () => true

```

#### 4.3 步骤2a：bypassPermissions 的双重触发条件

```TypeScript
// 代码块
const shouldBypassPermissions =
  appState.toolPermissionContext.mode === 'bypassPermissions' ||
  (appState.toolPermissionContext.mode === 'plan' &&
    appState.toolPermissionContext.isBypassPermissionsModeAvailable)

```

第二个条件很有趣：当用户以 `bypassPermissions` 模式启动，然后切换到 `plan` 模式时，`isBypassPermissionsModeAvailable` 为 `true`，此时 plan 模式下的操作仍然可以绕过权限。这允许用户在计划模式下预览操作，然后一键执行所有操作而无需逐一确认。

### 五、Auto 模式：AI 分类器决策

Auto 模式是 Claude Code 最复杂的权限机制，它用另一个 AI 模型来判断当前操作是否安全。

#### 5.1 决策流程

当 `hasPermissionsToUseTool` 收到 `ask` 结果，且当前模式是 `auto` 时：

```TypeScript
// 代码块
ask 结果
   |
   v
步骤A: 是否是不可分类器批准的安全检查？
   | YES -> 如果 headless 则 deny，否则返回 ask（让用户决定）
   | NO  |
         v
步骤B: tool.requiresUserInteraction()？
   | YES -> 返回 ask（AI 无法替代用户交互）
   | NO  |
         v
步骤C: acceptEdits 快速路径
   | 模拟 acceptEdits 模式检查：如果 acceptEdits 会允许，直接允许
   | （避免为安全操作调用昂贵的分类器 API）
   |
   v
步骤D: 安全工具白名单
   | isAutoModeAllowlistedTool(tool.name)？
   | YES -> 直接允许（无需分类器）
   | NO  |
         v
步骤E: 调用 yoloClassifier
   | classifyYoloAction(messages, action, tools, context, signal)
   |
   v
步骤F: 分类器结果处理
   | shouldBlock=false -> allow
   | shouldBlock=true  -> deny（记录 denial，检查是否超限）
   | unavailable       -> fail-closed（deny）或 fail-open（ask）
   | transcriptTooLong -> 回退到手动审批

```

#### 5.2 acceptEdits 快速路径：避免昂贵的 API 调用

```TypeScript
// 代码块
// 在调用分类器之前，先检查 acceptEdits 模式是否会允许
// 如果是，直接允许，无需调用分类器 API
if (result.behavior === 'ask' && tool.name !== AGENT_TOOL_NAME && tool.name !== REPL_TOOL_NAME) {
  const acceptEditsResult = await tool.checkPermissions(parsedInput, {
    ...context,
    getAppState: () => ({
      ...state,
      toolPermissionContext: { ...state.toolPermissionContext, mode: 'acceptEdits' },
    }),
  })
  if (acceptEditsResult.behavior === 'allow') {
    // 文件编辑等安全操作直接允许，不调用分类器
    return { behavior: 'allow', decisionReason: { type: 'mode', mode: 'auto' } }
  }
}

```

为什么排除 `AGENT_TOOL_NAME` 和 `REPL_TOOL_NAME`？因为这两个工具的 `checkPermissions` 在 `acceptEdits` 模式下会返回 `allow`，但它们实际上可能包含危险操作（REPL 代码可能包含 VM 逃逸）。

#### 5.3 Denial Tracking：防止分类器被滥用

```TypeScript
// 代码块
// src/utils/permissions/denialTracking.ts
export const DENIAL_LIMITS = {
  maxConsecutive: 3,   // 连续拒绝 3 次后回退到手动审批
  maxTotal: 20,        // 总拒绝 20 次后回退到手动审批
}

```

当分类器连续拒绝 3 次或总共拒绝 20 次时，系统会回退到手动审批模式，并显示警告：

```TypeScript
// 代码块
"3 consecutive actions were blocked. Please review the transcript before continuing."

```

这个设计防止了两种情况：一是模型陷入无限循环（不断尝试被拒绝的操作），二是分类器过于保守导致用户体验极差。

#### 5.4 Iron Gate：分类器不可用时的策略

```TypeScript
// 代码块
// 分类器不可用时，根据 feature flag 决定策略
if (classifierResult.unavailable) {
  if (getFeatureValue_CACHED_WITH_REFRESH('tengu_iron_gate_closed', true, 30 * 60 * 1000)) {
    // fail-closed：拒绝操作，要求用户重试
    return { behavior: 'deny', message: buildClassifierUnavailableMessage(...) }
  }
  // fail-open：回退到正常权限处理（让用户手动决定）
  return result
}

```

`tengu_iron_gate_closed` 是一个 GrowthBook feature flag，默认为 `true`（fail-closed）。这意味着当分类器 API 不可用时，默认拒绝操作，而不是放行。这是「安全优先」的设计——宁可让用户手动确认，也不要在分类器不可用时自动放行。

### 七、Headless 模式：无头 Agent 的权限处理

当 Claude Code 在无头模式（如 CI/CD 环境）下运行时，无法显示权限提示框。此时权限系统有特殊处理：

```TypeScript
// 代码块
// shouldAvoidPermissionPrompts = true 时
if (appState.toolPermissionContext.shouldAvoidPermissionPrompts) {
  // 1. 先运行 PermissionRequest Hooks，给 Hook 机会决策
  const hookDecision = await runPermissionRequestHooksForHeadlessAgent(...)
  if (hookDecision) return hookDecision

  // 2. 如果 Hook 没有决策，自动拒绝
  return {
    behavior: 'deny',
    message: AUTO_REJECT_MESSAGE(tool.name),
    decisionReason: { type: 'asyncAgent', reason: 'Permission prompts not available' }
  }
}

```

这个设计允许用户通过 Hooks 来控制无头模式下的权限决策，而不是简单地拒绝所有操作。

### 八、权限规则的持久化与同步

#### 8.1 规则的存储位置

```TypeScript
// 代码块
~/.claude/settings.json          - userSettings（全局）
<project>/.claude/settings.json  - projectSettings（项目）
<project>/.claude/settings.local.json - localSettings（本地，不提交 git）

```

#### 8.2 规则同步机制

```TypeScript
// 代码块
export function syncPermissionRulesFromDisk(
  toolPermissionContext: ToolPermissionContext,
  rules: PermissionRule[],
): ToolPermissionContext {
  // 1. 如果启用了 allowManagedPermissionRulesOnly，清除所有非策略来源的规则
  if (shouldAllowManagedPermissionRulesOnly()) {
    // 清除 userSettings / projectSettings / localSettings / cliArg / session
  }

  // 2. 清除所有磁盘来源的规则（防止删除规则后旧规则残留）
  for (const diskSource of ['userSettings', 'projectSettings', 'localSettings']) {
    for (const behavior of ['allow', 'deny', 'ask']) {
      context = applyPermissionUpdate(context, { type: 'replaceRules', rules: [], ... })
    }
  }

  // 3. 应用新规则
  return applyPermissionUpdates(context, convertRulesToUpdates(rules, 'replaceRules'))
}

```

关键设计：步骤2先清空所有磁盘规则，再应用新规则。这确保了「删除规则」操作能正确生效——如果不先清空，删除的规则会因为没有对应的 `replaceRules` 更新而残留。

#### 8.3 企业管控：allowManagedPermissionRulesOnly

当企业启用 `allowManagedPermissionRulesOnly` 时，只有 `policySettings` 和 `flagSettings` 中的规则有效，用户无法添加自己的规则。这是企业安全合规的重要机制。

### 九、权限决策的可观测性

#### 9.1 决策原因类型

```TypeScript
// 代码块
type PermissionDecisionReason =
  | { type: 'rule'; rule: PermissionRule }           // 规则决策
  | { type: 'mode'; mode: PermissionMode }           // 模式决策
  | { type: 'hook'; hookName: string; reason?: string } // Hook 决策
```

### 十、总结：权限系统的设计哲学

#### 10.1 纵深防御

权限系统有多道防线，每道防线独立工作：规则引擎（静态规则）、工具自检（`checkPermissions`）、安全路径检查（`safetyCheck`）、AI 分类器（动态判断）、Hooks（可编程拦截）。即使某道防线失效，其他防线仍然有效。

#### 10.2 最小权限原则

默认情况下，所有操作都需要用户确认（`default` 模式）。用户需要主动扩大权限（开启 `acceptEdits`、`bypassPermissions` 或 `auto` 模式），而不是主动限制权限。

#### 10.3 不可绕过的安全底线

某些操作无论如何都不能自动执行：安全路径（`.git/`、`.claude/`、shell 配置）的修改；需要用户交互的工具（`AskUserQuestionTool`）；企业策略规则（`policySettings`）。

#### 10.4 优雅降级

当高级功能不可用时，系统会优雅降级：分类器不可用 -> fail-closed（拒绝）或 fail-open（手动审批）；连续拒绝过多 -> 回退到手动审批；无头模式 -> 先运行 Hooks，再自动拒绝。

#### 10.5 完整决策流程图

```TypeScript
// 代码块
tool + input + context
         |
         v
[hasPermissionsToUseTool]
         |
         v
[hasPermissionsToUseToolInner]
  1a. deny 规则？ -> deny
  1b. ask 规则？  -> ask（或沙箱自动允许）
  1c. tool.checkPermissions()
  1d. 工具 deny？ -> deny
  1e. requiresUserInteraction？ -> ask
  1f. 内容 ask 规则？ -> ask
  1g. safetyCheck？ -> ask（bypass 免疫）
  2a. bypassPermissions？ -> allow
  2b. allow 规则？ -> allow
  3.  passthrough -> ask
         |
         v
[hasPermissionsToUseTool 后处理]
  allow -> 重置 denial 计数
  ask + dontAsk 模式 -> deny
  ask + auto 模式 ->
    safetyCheck（不可分类）-> deny/ask
    requiresUserInteraction -> ask
    acceptEdits 快速路径 -> allow

```

Claude Code 的权限系统是一个精心设计的多层安全架构。它在「安全」和「便利」之间找到了平衡：默认安全（每次询问），但提供了多种方式让用户根据自己的需求调整权限级别。AI 分类器的引入更是将权限决策从「规则匹配」提升到了「语义理解」，让系统能够处理规则无法覆盖的边界情况。

### 十一、给 mini-claude-code 的启示

mini-claude-code 的 `permissions.py` 已经实现了基础的权限询问逻辑，但 Claude Code 的权限系统有几个值得借鉴的设计：

```Python
// 代码块
# src/permissions.py - 对应 Claude Code 的权限决策流水线
from enum import Enum

class PermissionMode(Enum):
    DEFAULT = "default"       # 每次询问
    ACCEPT_EDITS = "accept_edits"  # 自动允许文件编辑
    BYPASS = "bypass"         # 允许所有（危险！）

# 安全路径：无论什么模式都必须询问
SAFETY_PATHS = ['.git/', '.claude/', '.ssh/', '.bashrc', '.zshrc']

def check_permission(tool_name: str, input: dict, mode: PermissionMode) -> str:
    """返回 'allow' / 'deny' / 'ask'"""

    # 1. 安全路径检查（bypass 免疫）
    if tool_name in ('FileEdit', 'FileWrite', 'Bash'):
        path = input.get('file_path') or input.get('command', '')
        if any(safe in path for safe in SAFETY_PATHS):
            return 'ask'  # 无论什么模式都要询问

    # 2. bypassPermissions 模式
    if mode == PermissionMode.BYPASS:
        return 'allow'

    # 3. acceptEdits 模式：文件编辑自动允许
    if mode == PermissionMode.ACCEPT_EDITS:
        if tool_name in ('FileEdit', 'FileWrite'):
            return 'allow'

    # 4. 默认：询问用户
    return 'ask'

```

**最值得移植的两个设计**：

第一，**安全路径的 bypass 免疫**。即使用户开启了 `--dangerously-skip-permissions`，修改 `.git/hooks`、`.bashrc` 等敏感路径也应该强制询问。这是防止提示注入攻击的最后一道防线。

第二，**规则持久化**。当用户回答「允许」时，提供「只允许一次」和「总是允许」两个选项。「总是允许」的规则写入配置文件，下次启动时自动加载，避免重复询问。这是 Claude Code 的 `allow` 规则机制的核心价值。
