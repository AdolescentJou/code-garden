> *版本：v2.1.88 · 文件：*`*src/services/compact/*`

### 一、从一次"失忆"说起

你和 Claude Code 合作了两个小时，读了几十个文件，执行了上百条命令。然后它突然告诉你：上下文快满了，需要压缩。

表面上看，Claude Code 把历史对话总结一下，删掉旧内容，继续工作——不就这样吗？

但真实的实现远比这复杂。压缩不能随便截断，截断点落在工具调用和工具结果之间会让 API 报错；压缩后模型会"忘记"刚才读过的文件，需要重新注入；压缩本身也要消耗 token，如果压缩失败还要有熔断机制。Claude Code 为此构建了一套精密的多层压缩系统。

这篇文章要带你深入 `src/services/compact/`，看清楚每一次压缩背后的完整决策链路。

> 压缩触发的判断逻辑位于 `queryLoop` 的每轮迭代开头（→ 参见**专题 01**：查询引擎与对话循环）；多 Agent 场景下每个子 Agent 有独立的上下文窗口，压缩在各自的 `queryLoop` 中独立触发（→ 参见**专题 09**：多 Agent 系统）。

### 二、压缩系统全景：四种机制

Claude Code 的上下文压缩不是单一机制，而是四种互补的策略，从轻量到重量依次排列：

```TypeScript
轻量 ←————————————————————————————→ 重量
  MicroCompact          AutoCompact
  (工具结果清理)    SessionMemory    (全量摘要)
                    Compact
                    (增量摘要)
```

| 机制 | 触发条件 | 代价 | 效果 |
| --- | --- | --- | --- |
| MicroCompact | 每次请求前 | 极低（无 API 调用） | 清理旧工具结果 |
| Time-based MC | 距上次响应超过阈值 | 极低 | 清理冷缓存工具结果 |
| SessionMemory Compact | 接近阈值 + SM 有内容 | 低（无摘要 API 调用） | 用 SM 替换历史 |
| AutoCompact | 接近阈值 | 高（一次 API 调用） | 全量摘要 |

### 三、Token 阈值体系

压缩系统围绕一套精心设计的阈值运作：

```TypeScript
// 有效上下文窗口 = 总窗口 - 为摘要输出预留的 token
// p99.99 的摘要输出为 17,387 tokens，预留 20,000
export function getEffectiveContextWindowSize(model: string): number {
  const reservedTokensForSummary = Math.min(
    getMaxOutputTokensForModel(model),
    MAX_OUTPUT_TOKENS_FOR_SUMMARY,  // 20,000
  )
  return contextWindow - reservedTokensForSummary
}

// AutoCompact 触发阈值 = 有效窗口 - 13,000 缓冲
export const AUTOCOMPACT_BUFFER_TOKENS = 13_000
export function getAutoCompactThreshold(model: string): number {
  return getEffectiveContextWindowSize(model) - AUTOCOMPACT_BUFFER_TOKENS
}

// 警告阈值（黄色）= 触发阈值 - 20,000
export const WARNING_THRESHOLD_BUFFER_TOKENS = 20_000

// 阻塞阈值（红色，禁止继续）= 有效窗口 - 3,000
export const MANUAL_COMPACT_BUFFER_TOKENS = 3_000
```

以 200K 窗口为例：

- 有效窗口：200K - 20K = 180K
- AutoCompact 触发：180K - 13K = 167K（约 83%）
- 警告阈值：167K - 20K = 147K（约 73%）
- 阻塞阈值：180K - 3K = 177K（约 88%）

### 四、MicroCompact：无 API 调用的轻量压缩

MicroCompact 是最轻量的压缩机制，在每次 API 请求前运行，通过清理旧工具结果来节省 token，**不需要任何 API 调用**。

#### 可压缩工具集合

```TypeScript
const COMPACTABLE_TOOLS = new Set<string>([
  FILE_READ_TOOL_NAME,    // Read
  ...SHELL_TOOL_NAMES,    // Bash
  GREP_TOOL_NAME,         // Grep
  GLOB_TOOL_NAME,         // Glob
  WEB_SEARCH_TOOL_NAME,   // WebSearch
  WEB_FETCH_TOOL_NAME,    // WebFetch
  FILE_EDIT_TOOL_NAME,    // Edit
  FILE_WRITE_TOOL_NAME,   // Write
])
```

这些工具的结果通常很大（文件内容、命令输出），但在多轮对话后往往已经过时。

#### 两条执行路径

**路径一：Cached MicroCompact（ant-only，实验性）**

利用 API 的 `cache_edits` 功能，在不修改本地消息内容的情况下，告诉服务器删除特定工具结果的缓存条目。这样既节省了 token，又不会破坏 Prompt Cache 的命中率：

```TypeScript
async function cachedMicrocompactPath(messages, querySource) {
  const mod = await getCachedMCModule()
  const state = ensureCachedMCState()

  // 注册所有可压缩工具结果
  for (const message of messages) {
    if (message.type === 'user') {
      for (const block of message.message.content) {
        if (block.type === 'tool_result' && compactableToolIds.has(block.tool_use_id)) {
          mod.registerToolResult(state, block.tool_use_id)
        }
      }
    }
  }

  const toolsToDelete = mod.getToolResultsToDelete(state)
  if (toolsToDelete.length > 0) {
    // 生成 cache_edits 块，在 API 层注入（不修改本地消息）
    const cacheEdits = mod.createCacheEditsBlock(state, toolsToDelete)
    pendingCacheEdits = cacheEdits
    // 本地消息不变，只是告诉服务器删除缓存
    return { messages }
  }
  return { messages }
}
```

**路径二：Time-based MicroCompact**

当距离上次 assistant 响应超过配置的时间阈值时触发。此时服务器缓存已经过期（冷缓存），直接修改本地消息内容，将旧工具结果替换为占位符：

```TypeScript
function maybeTimeBasedMicrocompact(messages, querySource) {
  const trigger = evaluateTimeBasedTrigger(messages, querySource)
  if (!trigger) return null

  const compactableIds = collectCompactableToolIds(messages)
  const keepRecent = Math.max(1, config.keepRecent)
  const keepSet = new Set(compactableIds.slice(-keepRecent))  // 保留最近 N 个
  const clearSet = new Set(compactableIds.filter(id => !keepSet.has(id)))

  // 将旧工具结果内容替换为占位符
  const result = messages.map(message => {
    if (message.type !== 'user') return message
    const newContent = message.message.content.map(block => {
      if (block.type === 'tool_result' && clearSet.has(block.tool_use_id)) {
        return { ...block, content: '[Old tool result content cleared]' }
      }
      return block
    })
    return { ...message, message: { ...message.message, content: newContent } }
  })

  return { messages: result }
}
```

### 五、AutoCompact：全量摘要压缩

当 token 使用量超过阈值时，AutoCompact 触发全量摘要压缩。这是代价最高但效果最彻底的机制。

#### 触发决策

```TypeScript
export async function shouldAutoCompact(
  messages: Message[],
  model: string,
  querySource?: QuerySource,
  snipTokensFreed = 0,
): Promise<boolean> {
  // 递归保护：摘要 Agent 和压缩 Agent 本身不触发压缩
  if (querySource === 'session_memory' || querySource === 'compact') return false

  if (!isAutoCompactEnabled()) return false

  // 实验性：reactive-only 模式下跳过主动压缩
  if (feature('REACTIVE_COMPACT') && getFeatureValue_CACHED_MAY_BE_STALE('tengu_cobalt_raccoon', false)) return false

  const tokenCount = tokenCountWithEstimation(messages) - snipTokensFreed
  const { isAboveAutoCompactThreshold } = calculateTokenWarningState(tokenCount, model)
  return isAboveAutoCompactThreshold
}
```

#### 熔断器：防止无限重试

```TypeScript
const MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3

export async function autoCompactIfNeeded(...) {
  // 熔断：连续失败 3 次后停止重试
  if (tracking?.consecutiveFailures >= MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES) {
    return { wasCompacted: false }
  }
  // ...
}
```

这个设计来自真实数据：BQ 统计显示有 1,279 个会话出现了 50+ 次连续失败（最多 3,272 次），每天浪费约 25 万次 API 调用。

#### 压缩流程

`compactConversation` 是核心函数，执行以下步骤：

```TypeScript
1. 执行 PreCompact Hooks（用户可注入自定义指令）
2. 调用 streamCompactSummary（生成摘要）
   ├── 优先路径：forked agent（复用 Prompt Cache 前缀）
   └── 降级路径：直接流式 API 调用
3. 清理 readFileState 和 loadedNestedMemoryPaths
4. 并行生成 post-compact 附件：
   ├── 最近读取的文件（最多 5 个，50K token 预算）
   ├── 异步 Agent 状态
   ├── Plan 文件（如果在 Plan 模式）
   ├── 已调用的 Skills（最多 25K token）
   └── 工具/MCP 指令增量
5. 执行 SessionStart Hooks
6. 创建 CompactBoundaryMessage（边界标记）
7. 执行 PostCompact Hooks
8. 返回 CompactionResult
```

### 六、Prompt Cache 共享：压缩的隐藏成本优化

压缩本身需要一次 API 调用，而这次调用的输入就是整个对话历史——恰好与主对话的 Prompt Cache 前缀相同。Claude Code 利用这一点，通过 `forked agent` 复用缓存：

```TypeScript
async function streamCompactSummary({ messages, summaryRequest, cacheSafeParams, ... }) {
  const promptCacheSharingEnabled = getFeatureValue_CACHED_MAY_BE_STALE(
    'tengu_compact_cache_prefix',
    true,  // 默认开启
  )

  if (promptCacheSharingEnabled) {
    try {
      // forked agent 使用与主线程相同的 cache key 参数
      // （system, tools, model, messages prefix, thinking config）
      // 注意：不能设置 maxOutputTokens，否则会改变 thinking config，破坏缓存
      const result = await runForkedAgent({
        promptMessages: [summaryRequest],
        cacheSafeParams,
        canUseTool: createCompactCanUseTool(),  // 禁止工具调用
        querySource: 'compact',
        maxTurns: 1,
        skipCacheWrite: true,
      })
      if (result && !result.isApiErrorMessage) {
        return result  // 缓存命中，节省大量 token
      }
    } catch (error) {
      // 降级到直接流式调用
    }
  }

  // 降级路径：直接流式 API 调用
  // ...
}
```

实验数据（2026年1月）：禁用缓存共享时，98% 的压缩请求是缓存未命中，每天产生约 380 亿 token 的 cache_creation 开销。

### 七、压缩提示词：九段式结构

压缩提示词是精心设计的，要求模型生成包含九个部分的结构化摘要：

```TypeScript
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.
[强制无工具前言]

Your task is to create a detailed summary...

Before providing your final summary, wrap your analysis in <analysis> tags...
[分析草稿区，最终会被 formatCompactSummary 剥离]

Your summary should include:
1. Primary Request and Intent（主要请求和意图）
2. Key Technical Concepts（关键技术概念）
3. Files and Code Sections（文件和代码片段）
4. Errors and fixes（错误和修复）
5. Problem Solving（问题解决）
6. All user messages（所有用户消息）
7. Pending Tasks（待处理任务）
8. Current Work（当前工作）
9. Optional Next Step（可选下一步）

REMINDER: Do NOT call any tools.
[强制无工具尾注]
```

`<analysis>` 标签是一个"思维草稿区"——模型在这里整理思路，但 `formatCompactSummary` 会在摘要注入对话前将其剥离，只保留 `<summary>` 部分。这是一种廉价的 Chain-of-Thought：提升摘要质量，但不增加后续对话的 token 消耗。

### 八、Prompt-Too-Long 重试：压缩本身也可能超限

一个有趣的边界情况：压缩请求本身也可能超过上下文限制（CC-1180）。这时系统会截断最旧的 API 轮次并重试：

```TypeScript
export function truncateHeadForPTLRetry(
  messages: Message[],
  ptlResponse: AssistantMessage,
): Message[] | null {
  const groups = groupMessagesByApiRound(messages)
  if (groups.length < 2) return null

  const tokenGap = getPromptTooLongTokenGap(ptlResponse)
  let dropCount: number
  if (tokenGap !== undefined) {
    // 精确计算：丢弃足够覆盖 tokenGap 的最旧轮次
    let acc = 0
    dropCount = 0
    for (const g of groups) {
      acc += roughTokenCountEstimationForMessages(g)
      dropCount++
      if (acc >= tokenGap) break
    }
  } else {
    // 无法解析 gap：保守地丢弃 20%
    dropCount = Math.max(1, Math.floor(groups.length * 0.2))
  }

  // 至少保留一个轮次（否则没有内容可摘要）
  dropCount = Math.min(dropCount, groups.length - 1)
  const sliced = groups.slice(dropCount).flat()

  // 如果截断后第一条是 assistant 消息，API 会拒绝（必须以 user 开头）
  // 插入合成的 user 标记消息
  if (sliced[0]?.type === 'assistant') {
    return [
      createUserMessage({ content: '[earlier conversation truncated for compaction retry]', isMeta: true }),
      ...sliced,
    ]
  }
  return sliced
}
```

最多重试 3 次（`MAX_PTL_RETRIES = 3`），每次丢弃更多历史。

### 九、Post-Compact 状态恢复

压缩后，模型失去了对话历史，但某些状态需要恢复。`compactConversation` 在摘要后并行生成多种附件：

#### 文件状态恢复

最近读取的文件（最多 5 个，50K token 预算）会被重新注入：

```TypeScript
export const POST_COMPACT_MAX_FILES_TO_RESTORE = 5
export const POST_COMPACT_TOKEN_BUDGET = 50_000
export const POST_COMPACT_MAX_TOKENS_PER_FILE = 5_000

export async function createPostCompactFileAttachments(
  readFileState: Record<string, { content: string; timestamp: number }>,
  toolUseContext: ToolUseContext,
  maxFiles: number,
  preservedMessages: Message[] = [],
): Promise<AttachmentMessage[]> {
  const preservedReadPaths = collectReadToolFilePaths(preservedMessages)
  const recentFiles = Object.entries(readFileState)
    .filter(([filename]) =>
      !shouldExcludeFromPostCompactRestore(filename) &&
      !preservedReadPaths.has(expandPath(filename))  // 跳过已在保留消息中的文件
    )
    .sort((a, b) => b[1].timestamp - a[1].timestamp)  // 最近访问优先
    .slice(0, maxFiles)

  // 并行重新读取文件（获取最新内容）
  const results = await Promise.all(
    recentFiles.map(async file => generateFileAttachment(file.filename, ...))
  )

  // 按 token 预算过滤
  let usedTokens = 0
  return results.filter(result => {
    const tokens = roughTokenCountEstimation(jsonStringify(result))
    if (usedTokens + tokens <= POST_COMPACT_TOKEN_BUDGET) {
      usedTokens += tokens
      return true
    }
    return false
  })
}
```

排除规则：Plan 文件和 CLAUDE.md 文件不通过此机制恢复（它们有专门的恢复路径）。

#### Skills 状态恢复

已调用的 Skills 内容也会被恢复，但有截断机制：

```TypeScript
export const POST_COMPACT_MAX_TOKENS_PER_SKILL = 5_000
export const POST_COMPACT_SKILLS_TOKEN_BUDGET = 25_000

export function createSkillAttachmentIfNeeded(agentId?: string): AttachmentMessage | null {
  const invokedSkills = getInvokedSkillsForAgent(agentId)

  let usedTokens = 0
  const skills = Array.from(invokedSkills.values())
    .sort((a, b) => b.invokedAt - a.invokedAt)  // 最近调用优先
    .map(skill => ({
      name: skill.skillName,
      path: skill.skillPath,
      content: truncateToTokens(skill.content, POST_COMPACT_MAX_TOKENS_PER_SKILL),
    }))
    .filter(skill => {
      const tokens = roughTokenCountEstimation(skill.content)
      if (usedTokens + tokens > POST_COMPACT_SKILLS_TOKEN_BUDGET) return false
      usedTokens += tokens
      return true
    })

  return createAttachmentMessage({ type: 'invoked_skills', skills })
}
```

截断时保留文件头部（setup/usage 指令通常在开头），并附加提示：`[... skill content truncated; use Read on the skill path if you need the full text]`。

### 十、Session Memory Compact：无摘要 API 调用的增量压缩

Session Memory Compact 是一种实验性机制（需要 `tengu_session_memory` + `tengu_sm_compact` feature flag），利用后台持续更新的 Session Memory 作为摘要，避免压缩时的 API 调用：

```TypeScript
传统 AutoCompact：
  对话历史 → [API 调用生成摘要] → 摘要 + 最近消息

Session Memory Compact：
  对话历史 → [直接使用 Session Memory] → SM 内容 + 最近消息
```

#### 保留消息计算

SM Compact 的关键是决定保留哪些最近消息（不被摘要替换）：

```TypeScript
export function calculateMessagesToKeepIndex(
  messages: Message[],
  lastSummarizedIndex: number,
): number {
  const config = getSessionMemoryCompactConfig()
  // 默认：minTokens=10K, minTextBlockMessages=5, maxTokens=40K

  let startIndex = lastSummarizedIndex + 1  // 从上次摘要位置之后开始

  // 向前扩展，直到满足最小要求
  for (let i = startIndex - 1; i >= floor; i--) {
    totalTokens += estimateMessageTokens([messages[i]])
    if (hasTextBlocks(messages[i])) textBlockMessageCount++
    startIndex = i

    if (totalTokens >= config.maxTokens) break  // 硬上限
    if (totalTokens >= config.minTokens && textBlockMessageCount >= config.minTextBlockMessages) break
  }

  // 调整以避免分割 tool_use/tool_result 对
  return adjustIndexToPreserveAPIInvariants(messages, startIndex)
}
```

#### API 不变量保护

`adjustIndexToPreserveAPIInvariants` 解决了一个微妙的问题：如果截断点恰好落在 `tool_use` 和 `tool_result` 之间，API 会报错（孤立的 tool_result）。函数会向前调整截断点，确保配对完整：

```TypeScript
export function adjustIndexToPreserveAPIInvariants(
  messages: Message[],
  startIndex: number,
): number {
  // 步骤1：收集保留范围内所有 tool_result 的 ID
  const allToolResultIds = collectToolResultIds(messages.slice(startIndex))

  // 步骤2：找到对应的 tool_use，如果在保留范围外，向前扩展
  for (let i = adjustedIndex - 1; i >= 0 && neededToolUseIds.size > 0; i--) {
    if (hasToolUseWithIds(messages[i], neededToolUseIds)) {
      adjustedIndex = i  // 向前扩展
    }
  }

  // 步骤3：处理 thinking 块（同一 message.id 的多个流式块）
  // 如果保留范围内有 assistant 消息，其 thinking 块可能在前面的消息中
  for (let i = adjustedIndex - 1; i >= 0; i--) {
    if (messages[i].type === 'assistant' &&
        messageIdsInKeptRange.has(messages[i].message.id)) {
      adjustedIndex = i  // 包含 thinking 块
    }
  }

  return adjustedIndex
}
```

### 十一、Partial Compact：精确控制压缩范围

除了全量压缩，Claude Code 还支持部分压缩——用户可以选择一条消息，压缩其前面或后面的内容：

```TypeScript
export async function partialCompactConversation(
```

两种方向：

### 十二、CompactBoundaryMessage：压缩历史的锚点

每次压缩都会创建一个 `SystemCompactBoundaryMessage`，作为压缩历史的锚点：

```TypeScript
const boundaryMarker = createCompactBoundaryMessage(

// 携带压缩前已发现的工具（用于 deferred tool schema 过滤）
if (preCompactDiscovered.size > 0) {

// 对于保留了部分消息的压缩，记录保留段的边界
boundaryMarker.compactMetadata.preservedSegment = {
  headUuid: messagesToKeep[0].uuid,
```

边界标记的作用：

- `getMessagesAfterCompactBoundary` 用它找到压缩后的有效消息范围
- 会话恢复时用它重建消息链
- 防止旧的压缩边界被重复处理

### 十三、图像剥离：防止压缩请求本身超限

压缩请求发送整个对话历史，但图像会大幅增加 token 消耗（尤其是 CCD 会话中用户频繁附图）。`stripImagesFromMessages` 在发送前替换所有图像：

```TypeScript
export function stripImagesFromMessages(messages: Message[]): Message[] {
  return messages.map(message => {
    if (message.type !== 'user') return message

    const newContent = content.flatMap(block => {
      if (block.type === 'image') return [{ type: 'text', text: '[image]' }]
      if (block.type === 'document') return [{ type: 'text', text: '[document]' }]
      // 也处理 tool_result 内嵌的图像
      if (block.type === 'tool_result' && Array.isArray(block.content)) {
        return [{ ...block, content: block.content.map(item =>
          item.type === 'image' ? { type: 'text', text: '[image]' } : item
        )}]
      }
      return [block]
    })
    return { ...message, message: { ...message.message, content: newContent } }
  })
}
```

### 十四、Keep-alive：防止压缩期间连接超时

压缩 API 调用可能需要 5-10 秒，期间没有其他消息流过 WebSocket，服务器可能因空闲超时断开连接。系统通过两种方式保持连接：

```TypeScript
const activityInterval = isSessionActivityTrackingActive()
  ? setInterval(
      (statusSetter) => {
        sendSessionActivitySignal()    // PUT /worker 心跳
        statusSetter?.('compacting')   // 重新发送 'compacting' 状态
      },
      30_000,  // 每 30 秒
      context.setSDKStatus,
    )
  : undefined

try {
  // 执行压缩...
} finally {
  clearInterval(activityInterval)  // 压缩完成后清理
}
```

### 十五、架构总结

Claude Code 的上下文压缩系统体现了几个核心设计原则：

**分层防御**：从轻量的 MicroCompact（无 API 调用）到重量的 AutoCompact（全量摘要），多层机制互补，在不同场景下选择最合适的策略。

**缓存感知**：Prompt Cache 共享让压缩 API 调用几乎免费（98% 缓存命中）；Cached MicroCompact 通过 cache_edits 在不破坏缓存的情况下删除工具结果；Time-based MC 在缓存已冷时才直接修改内容。

**状态保全**：压缩不是简单地丢弃历史，而是精心恢复关键状态——最近读取的文件、已调用的 Skills、Plan 文件、Plan 模式指令、工具/MCP 增量。

**API 不变量保护**：`adjustIndexToPreserveAPIInvariants` 确保截断点不会分割 tool_use/tool_result 对或 thinking 块，防止 API 报错。

**熔断与降级**：连续失败 3 次后停止重试；forked agent 失败时降级到直接流式调用；PTL 重试最多 3 次后报错而非无限循环。

### 十六、给 mini-claude-code 的启示

如果要在最小实现中支持上下文压缩，核心骨架只需三步：

```Python
# mini-claude-code 的极简压缩实现
COMPACT_THRESHOLD = 0.8  # 超过上下文窗口 80% 时触发

async def maybe_compact(messages: list, model: str) -> list:
    """检查是否需要压缩，需要则生成摘要替换历史"""
    token_count = estimate_tokens(messages)
    context_window = get_context_window(model)

    if token_count < context_window * COMPACT_THRESHOLD:
        return messages  # 不需要压缩

    # 生成摘要（调用一次 API）
    summary = await generate_summary(messages)

    # 用摘要替换历史，只保留最近几条消息
    recent = messages[-4:]  # 保留最近 2 轮对话
    return [
        {"role": "user", "content": f"[Previous conversation summary]\n{summary}"},
        {"role": "assistant", "content": "Understood. Continuing from the summary."},
        *recent,
    ]
```

这个骨架只有 20 行，但已经包含了压缩的核心逻辑。真实实现在此基础上叠加了：

- **MicroCompact**：在调用 API 前先清理旧工具结果，无需额外 API 调用（最高性价比的优化）
- **Prompt Cache 共享**：压缩请求复用主对话的 cache key，让压缩几乎免费
- **状态恢复**：压缩后重新注入最近读取的文件、已调用的 Skills，防止模型「失忆」
- **API 不变量保护**：截断点不能落在 tool_use/tool_result 对之间，否则 API 报错
- **熔断器**：连续失败 3 次后停止重试，防止无限循环浪费 API 调用

对于 mini-claude-code，**最值得优先实现的是 MicroCompact**：在每次 API 调用前，把超过 N 轮的工具结果内容替换为 `[cleared]` 占位符。这个优化零成本（无 API 调用），却能显著延长会话寿命。
