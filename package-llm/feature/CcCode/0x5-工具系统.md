### 一、从一次工具调用说起

你让 Claude Code 帮你修一个 bug。它读了文件，搜了代码，执行了测试，最后改了几行——一气呵成。

表面上看，Claude 决定用什么工具，调用一下，拿到结果，继续思考——不就这样吗？

但真实的实现远比这复杂。工具调用需要 JSON Schema 校验、业务逻辑校验、权限检查，多个工具可以并发执行但有并发安全限制，工具结果超过 token 上限要截断，MCP 工具和内置工具要统一调度。Claude Code 为此构建了一套完整的工具系统，支撑着 80+ 内置工具的注册、调度与执行。

这篇文章要带你深入这套工具系统，看清楚每一次工具调用背后的完整链路。

整个工具系统可以分为四层：

```TypeScript
// 代码块
+------------------------------------------------------------------+
|                        Tool 接口层                               |
|  Tool.ts：定义 20+ 个方法的接口，buildTool 提供安全默认值         |
+------------------------------------------------------------------+
|                        调度编排层                                |
|  toolOrchestration.ts：partitionToolCalls 并发/串行分批          |
+------------------------------------------------------------------+
|                        执行流水线层                              |
|  toolExecution.ts：校验 -> 权限 -> Hooks -> 执行 -> PostHooks   |
+------------------------------------------------------------------+
|                        具体工具层                                |
|  BashTool / FileEditTool / FileReadTool / MCPTool / ...         |
+------------------------------------------------------------------+

```

> 工具执行流水线中的权限决策由专门的权限系统负责（→ 参见**专题 06**：权限系统）；MCP 工具的连接管理和工具发现有独立的子系统（→ 参见**专题 08**：MCP 协议）；Hooks 在工具执行前后拦截（→ 参见**专题 10**：Hooks 系统）。

### 二、Tool 接口：20+ 个方法的设计哲学

#### 2.1 核心接口定义

`src/Tool.ts` 定义了 `Tool` 接口，这是整个工具系统的契约：

```TypeScript
// 代码块
export interface Tool<TInput = unknown, TOutput = unknown> {
  // 基础标识
  name: string
  aliases?: string[]          // 向后兼容的别名（如 KillShell -> TaskStop）
  description: string
  inputSchema: ZodSchema<TInput>

  // 核心执行
  call(
    input: TInput,
    context: ToolUseContext & { toolUseId: string; userModified: boolean },
    canUseTool: CanUseToolFn,
    assistantMessage: AssistantMessage,
    onProgress: (progress: ToolProgress<ToolProgressData>) => void,
  ): Promise<ToolResult<TOutput>>

  // 并发安全性（调度层关键字段）
  isConcurrencySafe?: (input: TInput) => boolean

  // 权限检查
  checkPermissions?: (
    input: TInput,
    context: ToolUseContext,
  ) => Promise<PermissionResult>

  // 输入校验（Zod 之外的业务逻辑校验）
  validateInput?: (
    input: TInput,
    context: ToolUseContext,
  ) => Promise<{ result: boolean; message?: string; errorCode?: string } | undefined>

  // 结果映射
  mapToolResultToToolResultBlockParam(
    result: TOutput,
    toolUseId: string,
  ): ToolResultBlockParam

  // 可观测性
  backfillObservableInput?: (input: Record<string, unknown>) => void
  renderToolUseMessage?: (input: TInput, context: ToolUseContext) => React.ReactNode
  renderToolResultMessage?: (output: TOutput, context: ToolUseContext) => React.ReactNode

  // 其他
  isMcp?: boolean
  maxResultSizeChars?: number
  isReadOnly?: () => boolean
  isEnabled?: () => boolean
}

```

#### 2.2 buildTool：安全默认值工厂

直接实现 `Tool` 接口需要填写大量字段。`buildTool` 函数提供了合理的默认值，让工具开发者只需关注核心逻辑：

```TypeScript
// 代码块
export function buildTool<TInput, TOutput>(
  config: ToolConfig<TInput, TOutput>,
): Tool<TInput, TOutput> {
  return {
    // 默认：所有工具都不是并发安全的（保守策略）
    isConcurrencySafe: () => false,

    // 默认：结果直接转为文本
    mapToolResultToToolResultBlockParam: (result, toolUseId) => ({
      type: 'tool_result',
      tool_use_id: toolUseId,
      content: typeof result === 'string' ? result : JSON.stringify(result),
    }),

    // 默认：无最大结果大小限制
    maxResultSizeChars: undefined,

    ...config,
  }
}

```

关键设计决策：`**isConcurrencySafe 默认返回 false**`。这意味着除非工具明确声明自己是并发安全的，否则调度层会将其串行执行。这是「安全优先」的设计——宁可慢一点，也不要出现竞态条件。

#### 2.3 ToolUseContext：工具执行的上下文容器

每次工具调用都会收到一个 `ToolUseContext`，它包含了工具执行所需的一切：

```TypeScript
// 代码块
export interface ToolUseContext {
  messages: Message[]                    // 消息历史
  getAppState: () => AppState            // 应用状态（权限模式、工作目录等）
  abortController: AbortController       // 中止信号（用户按 Ctrl+C 时触发）
  options: QueryOptions                  // 工具列表、MCP 客户端等

  agentId?: string                       // Agent 相关

  toolDecisions?: Map<string, ToolDecisionInfo>  // 权限系统使用
}

```

### 三、调度编排：partitionToolCalls 的并发策略

#### 3.1 问题背景

当模型在一次响应中调用多个工具时，如何执行这些工具？全部串行太慢，全部并发可能出现竞态。Claude Code 的解决方案是**按并发安全性分批**。

#### 3.2 partitionToolCalls 算法

```TypeScript
// 代码块
// src/services/tools/toolOrchestration.ts
export function partitionToolCalls(
  toolUses: ToolUseBlock[],
  tools: readonly Tool[],
): ToolUseBlock[][] {
  const batches: ToolUseBlock[][] = []
  let currentBatch: ToolUseBlock[] = []

  for (const toolUse of toolUses) {
    const tool = findToolByName(tools, toolUse.name)
    const input = toolUse.input as Record<string, unknown>
    const isSafe = tool?.isConcurrencySafe?.(input as never) ?? false

    if (isSafe) {
      // 并发安全：加入当前批次
      currentBatch.push(toolUse)
    } else {
      // 不安全：先提交当前批次，再单独成批
      if (currentBatch.length > 0) {
        batches.push(currentBatch)
        currentBatch = []
      }
      batches.push([toolUse])  // 写工具独占一个批次
    }
  }

  if (currentBatch.length > 0) {
    batches.push(currentBatch)
  }

  return batches
}

```

#### 3.3 执行策略可视化

```TypeScript
// 代码块
输入工具序列：[Read(A), Read(B), Edit(C), Read(D), Bash(E)]
并发安全性：   [true,    true,    false,   true,    false  ]

分批结果：
  批次1: [Read(A), Read(B)]  ->  Promise.all() 并发执行
  批次2: [Edit(C)]           ->  串行执行
  批次3: [Read(D)]           ->  Promise.all() 并发执行
  批次4: [Bash(E)]           ->  串行执行

```

注意：`Read(D)` 虽然是只读操作，但因为前面有不安全的 `Edit(C)`，它被迫单独成批。这是算法的保守之处——一旦遇到不安全工具，后续的安全工具也无法与之前的批次合并。

#### 3.4 哪些工具是并发安全的？

声明 `isConcurrencySafe` 返回 `true` 的工具主要是只读工具：`FileReadTool`（读文件，无副作用）、`GlobTool`（文件名搜索，无副作用）、`GrepTool`（内容搜索，无副作用）、`LSPTool`（语言服务器查询，无副作用）。

写操作工具（`BashTool`、`FileEditTool`、`FileWriteTool`）默认不安全，因为它们可能修改文件系统状态。

### 四、执行流水线：checkPermissionsAndCallTool 的八个阶段

`toolExecution.ts` 中的 `checkPermissionsAndCallTool` 是工具执行的核心流水线，共经历八个阶段：

**阶段1：Zod Schema 校验**。`tool.inputSchema.safeParse(input)` 对输入做类型校验，失败则返回 `InputValidationError` 和 `schemaHint`。

**阶段2：业务逻辑校验**。`tool.validateInput?.(parsedInput, context)` 做 Zod 之外的语义校验，失败则返回工具特定错误。

**阶段3：投机性分类器（仅 BashTool）**。`startSpeculativeClassifierCheck(command, ...)` 与后续步骤并行运行，减少等待时间。

**阶段4：_simulatedSedEdit 防御剥离（仅 BashTool）**。强制移除模型可能注入的内部字段。

**阶段5：PreToolUse Hooks**。`runPreToolUseHooks(...)` 可修改 input、拒绝执行、提供权限决策。

**阶段6：权限决策**。`resolveHookPermissionDecision()` 调用 `canUseTool()`，deny 则返回错误并可能触发 PermissionDenied Hook。

**阶段7：工具执行**。`tool.call(callInput, context, ...)` 在 OTel span 追踪下执行，记录耗时。

**阶段8：PostToolUse Hooks**。`runPostToolUseHooks(...)` 对 MCP 工具可修改输出后再提交。

#### 4.1 投机性分类器：性能优化的典范

```TypeScript
// 代码块
// 在权限检查之前，提前启动 BashTool 的 allow 分类器
// 它与 PreToolUse Hooks 并行运行
if (tool.name === BASH_TOOL_NAME && 'command' in parsedInput.data) {
  startSpeculativeClassifierCheck(
    command,
    appState.toolPermissionContext,
    abortController.signal,
    isNonInteractiveSession,
  )
}

```

没有投机性启动时，总耗时约 150ms（Hooks 50ms + 分类器 100ms 串行）。有投机性启动时，两者并行，总耗时约 50ms（取最长者）。

#### 4.2 callInput 的三次变形

权限系统看到展开后的绝对路径（安全），工具结果嵌入原始路径（稳定）。这是因为工具结果会把路径嵌入字符串，如果路径被展开，VCR 测试的 fixture hash 就会失效。

```TypeScript
// 代码块
let callInput = processedInput          // 最终传给 tool.call() 的（保留原始路径）
const backfilledClone = tool.backfillObservableInput
  ? { ...processedInput }              // 浅拷贝
  : null
if (backfilledClone) {
  tool.backfillObservableInput!(backfilledClone)  // 展开 ~/foo -> /home/user/foo
  processedInput = backfilledClone     // hooks/权限 看到展开后的绝对路径
}

```

### 五、BashTool 深度解析

#### 5.1 _simulatedSedEdit：安全设计的典范

`_simulatedSedEdit` 是 BashTool 最有趣的设计。当 Claude 生成 `sed -i 's/old/new/g' file.txt` 这样的命令时，用户看不到具体改了什么。Claude Code 的解决方案是**把 sed 命令转换成结构化的文件编辑操作**，让用户能看到 diff。

流程如下：模型生成 sed 命令 -> 权限系统检测到 sed 模式 -> 生成 `SedEditPermissionRequest` 展示 diff 给用户 -> 用户批准 -> 权限系统注入 `_simulatedSedEdit` 到 input -> `BashTool.call()` 检测到该字段 -> 不执行 bash，直接做 Node.js 层面的字符串替换。

而 `toolExecution.ts` 里的防御代码确保模型无法直接注入这个字段：

```TypeScript
// 代码块
// Defense-in-depth: strip _simulatedSedEdit from model-provided Bash input
if (tool.name === BASH_TOOL_NAME && '_simulatedSedEdit' in processedInput) {
  const { _simulatedSedEdit: _, ...rest } = processedInput
  processedInput = rest  // 强制剥离
}

```

这是典型的**纵深防御**：Zod schema 的 `strictObject` 是第一道防线，这里的显式剥离是第二道防线。

#### 5.2 超时与进度报告

### 六、FileEditTool：精确的字符串替换

#### 6.1 唯一性校验

FileEditTool 的核心设计原则：`old_string` 必须在文件中唯一出现。

```TypeScript
// 代码块
async validateInput(input, context) {
  const { file_path, old_string } = input
  const content = await readFile(file_path)

  const occurrences = countOccurrences(content, old_string)
  if (occurrences === 0) {
    return { result: false, message: `old_string not found in file` }
  }
  if (occurrences > 1) {
    return {
      result: false,
      message: `Found ${occurrences} occurrences. Provide more context to uniquely identify the location.`
    }
  }
  return { result: true }
}

```

这个设计迫使模型提供足够的上下文来唯一定位替换位置，避免意外修改错误的代码段。这也解释了为什么 Claude Code 在编辑文件时总是要求提供足够多的上下文行。

#### 6.2 为什么不用行号？

行号方案的问题：当文件被其他工具修改后，行号会失效。基于文本内容的匹配更加稳健——只要上下文足够唯一，就能精确定位，即使文件在此之前被修改过。

### 七、MCP 工具：动态扩展机制

#### 7.1 命名规范

MCP 工具名格式：`mcp__{serverName}__{toolName}`，其中 serverName 经过 `normalizeNameForMCP` 处理（例如 "[claude.ai](http://claude.ai) Slack" 变为 "claude_ai_Slack"）。

#### 7.2 MCP 工具的特殊执行路径

在 `toolExecution.ts` 中，MCP 工具有一处特殊处理：非 MCP 工具立即添加工具结果（性能优先），而 MCP 工具在 PostToolUse Hooks 之后才添加工具结果（允许 Hook 修改输出）。

```TypeScript
// 代码块
// 非 MCP 工具：立即添加工具结果（性能优先）
if (!isMcpTool(tool)) {
  await addToolResult(toolOutput, mappedToolResultBlock)
}

// 运行 PostToolUse Hooks（MCP 工具的输出可被修改）
for await (const hookResult of runPostToolUseHooks(...)) {
  if ('updatedMCPToolOutput' in hookResult && isMcpTool(tool)) {
    toolOutput = hookResult.updatedMCPToolOutput
  }
}

// MCP 工具：在 Hooks 之后才添加工具结果
if (isMcpTool(tool)) {
  await addToolResult(toolOutput)
}

```

#### 7.3 支持的传输协议

Claude Code 支持 8 种 MCP 传输协议：`stdio`（本地进程，最常用）、`sse`（Server-Sent Events）、`http`、`ws`（WebSocket）、`sdk`（SDK 内嵌）、`sse-ide`（IDE 集成 SSE）、`ws-ide`（IDE 集成 WebSocket）、`claudeai-proxy`（[Claude.ai](http://Claude.ai) 平台代理）。

### 八、工具别名：向后兼容的优雅处理


### 十、总结：工具系统的设计哲学

Claude Code 的工具系统体现了三个核心设计哲学。

**安全优先**：`isConcurrencySafe` 默认 `false`，宁可慢也不要竞态；双层输入校验（Zod 类型 + 业务语义）；`_simulatedSedEdit` 纵深防御（schema 拒绝 + 显式剥离）；别名兼容让旧工具名不会报错。

**性能优化**：投机性分类器让 BashTool 权限检查与 Hooks 并行；只读工具并发通过 `partitionToolCalls` 智能分批；结果预映射让 `mappedToolResultBlock` 只计算一次。

**可扩展性**：`buildTool` 提供安全默认值，新工具只需实现 4 个字段；MCP 协议让第三方工具无需修改源码即可接入；Hooks 系统提供可编程的工具拦截，支持修改输入/输出/权限决策。

理解这套系统，是理解 Claude Code 如何把 LLM 的文本输出转化为真实世界操作的关键。

### 十一、给 mini-claude-code 的启示

mini-claude-code 的工具系统已经实现了核心骨架（`tool.py`、`tools/` 目录），但有几个 Claude Code 的设计值得参考：

```Python
// 代码块
# src/tool.py - 工具基类，对应 Claude Code 的 Tool 接口
from abc import ABC, abstractmethod
from typing import Any

class Tool(ABC):
    name: str
    description: str

    # 关键：声明是否并发安全（对应 isConcurrencySafe）
    is_concurrency_safe: bool = False  # 默认保守：不并发

    @abstractmethod
    async def call(self, input: dict, context: dict) -> str:
        pass

    def validate_input(self, input: dict) -> tuple[bool, str]:
        """业务逻辑校验（Zod 之外的语义校验）"""
        return True, ""

# 工具调度：按并发安全性分批执行
async def execute_tool_calls(tool_uses: list, tools: dict) -> list:
    results = []
    i = 0
    while i < len(tool_uses):
        tool = tools.get(tool_uses[i]['name'])
        if tool and tool.is_concurrency_safe:
            # 收集连续的并发安全工具
            batch = []
            while i < len(tool_uses):
                t = tools.get(tool_uses[i]['name'])
                if t and t.is_concurrency_safe:
                    batch.append(tool_uses[i])
                    i += 1
                else:
                    break
            # 并发执行这一批
            batch_results = await asyncio.gather(*[
                tools[tu['name']].call(tu['input'], {}) for tu in batch
            ])
            results.extend(batch_results)
        else:
            # 串行执行不安全工具
            result = await tool.call(tool_uses[i]['input'], {})
            results.append(result)
            i += 1
    return results

```

**最值得移植的三个设计**：

第一，`isConcurrencySafe` 默认 `false` 的保守策略。mini-claude-code 的 `FileReadTool`、`GrepTool` 可以声明为并发安全，让模型同时读取多个文件时真正并行执行，显著提升速度。

第二，`validateInput` 的两层校验。Schema 校验（类型正确）之外，还需要业务校验（如 `FileEditTool` 的 `old_string` 唯一性检查）。把这两层分开，错误信息更清晰，模型更容易理解并修正。

第三，工具结果大小限制（`maxResultSizeChars`）。大文件读取、长命令输出会消耗大量 token，应该在工具层截断并提示模型，而不是让上下文悄悄膨胀。
