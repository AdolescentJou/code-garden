# simple-code：用1000行代码实现一个Coding Agent

Claude Code是一款AI Coding工具，内置一个LLM驱动的Agent，用户可以通过自然语言与其对话并下发任务，Agent能自主规划，操作本地文件，完成编程任务。本文会介绍一些当前Agent应用相关的概念，带你用几百行代码手写一个simple-code agent以了解其基本原理，最后介绍如何构建一个生产级应用mini-claude-code。

> simple-code代码见 [DevTools Code 链接](https://dev.sankuai.com/code/repo-detail/~DONGRUICHEN/simple-claude-code/file/list)

## 【1】与大语言模型(LLM)交互

LLM是现阶段一切AI Agent的起点，可以将其看做吸收了全世界公开知识的大学生，你可以通过自然语言指令控制其做任何事情。

在形式上，LLM通常接收一段文本输入，并输出一段文本，因为LLM接收过强化学习指令微调，因此能识别输入的指令并给出回应。比如:

**输入：**

> 给我说两个科学家名字

**LLM输出：**

> 当然，以下是两位著名的科学家：
>
> **阿尔伯特·爱因斯坦 (Albert Einstein)** - 著名的理论物理学家，以相对论和光电效应闻名。
>
> **玛丽·居里 (Marie Curie)** - 著名的化学家和物理学家，以研究放射性物质而著称。
>
> 如果你有更多关于科学家的问题或需要其他信息，请告诉我！

通常我们使用云服务厂商提供的LLM交互能力，通过http请求发送消息，并获取LLM的输出。

### 给LLM发送消息

如下curl是一次最简单的调用，其中有三个参数：

- **model**：模型名称
- **messages**：历史交互信息
- **stream**：是否流式输出。由于LLM通常为自回归模型，每次输出一个字符，将新输出的字符作为输入，再获取新的输出。因此一次完整的回复是逐渐生成的，客户端可以通过该参数是否流式接收输出还是等待输出结束再一次返回。

这里最重要的就是 `messages` 参数，因为LLM和http请求都是无状态的，因此每一次请求都需要将历史的交互信息一并发送。消息格式如下所示，`role` 表示谁输出的内容，`content` 表示具体的内容，相当于以第三人称的形式去记录用户与LLM的交互。

- **system**：表示该内容是对LLM的系统设定，用以约束assistant回复的内容
- **user**：表示用户输入的内容
- **assistant**：表示LLM输出的内容
- **tool**：表示工具执行的结果（后面解释）

> 假设你在跟LLM聊天，LLM每次只能记住你当前说的话，为了让LLM知道之前发生了什么，你每次对话都需要将历史的对话记录一起告诉他。

## 【3】构建Agent

> LLM仅能输出文本内容，基于LLM构建Agent，才能自主完成Coding任务。

Agent是一个抽象概念，它是指以LLM为核心，并由工具、提示等多个模块构成的一个对外表现智能的抽象体。Agent的定义有很多，这里借用anthropic的定义：即能通过LLM实现自主规划和任务执行，通过工具使用来完成任务。

但LLM只能输出文本，是如何执行工具或影响外部世界的呢？答案是**编码**，将Agent与外部交互的方式用文本编码，比如编码为JSON格式，LLM输出特定的文本，通过程序解析后执行并返回执行的结果。

> 当前繁荣的互联网世界，底层也是由一个个0和1编码构成。

anthropic将一个Agent执行任务的流程定义如下：

它构造了一个循环，Agent在循环中不断自我迭代直到完成任务。其中每一步可映射为具体的代码实现：

- **任务规划、做出决策、检查任务状态、输出结果**：这些本质都是LLM输出的文本，以文本描述来具象化这几个过程
- **调用工具**：由于LLM只能输出文本，因此会将工具列表以文本形式传递给LLM，LLM输出特定格式文本，表明要执行的工具以及相关参数，然后在代码里解析文本并执行
- **获取执行结果**：将代码执行结果以文本形式发送给LLM

因此，将Agent的构建分为两步：

1. 构建工具列表
2. 构建循环执行流程

### 工具构建

#### 工具定义

工具定义包含三部分：

- **工具名**：用于识别Agent调用哪一个工具
- **工具描述**：声明工具的功能，用以Agent决策是否调用
- **工具参数**：声明使用该工具需要Agent提供的额外信息。其中，工具参数声明使用 [JSON Schema](https://json-schema.org/) 实现

#### 工具传递

在模型调用的http接口里，通过一个额外的 `tools` 参数将工具定义的列表传递。

#### 工具调用

如果LLM需要调用工具，会返回如下格式的消息，其中message里额外有一个 `tool_calls` 字段表明需要调用工具：

- `id`：唯一表示这次调用，用于后边识别工具执行结果
- `function.name` 和 `function.arguments`：表明要调用的工具以及工具依赖的参数

> 这里表示使用bash工具，执行命令 `ls -la`

#### 工具结果传递

工具结果放在messages里传递给LLM，通过 `role: tool` 表明是工具执行结果，`tool_call_id` 表明是哪一次工具调用。

### 循环执行流程

> 循环是实现Agent自主执行直到任务完成的关键。

整个循环执行流程实现很简单，通过system prompt来实现Agent的自主规划和决策。

代码层面，只需要判断是否有工具调用，有则将执行结果拼接在messages里继续调用LLM，没有则输出结果。

首先开发bash工具，包括工具定义和执行函数。

然后开发Agent对象，包含 `run`、`toolExecute`、`agentLoop` 三个方法：

- **run**：接收用户输入，启动Agent执行任务，并打印任务执行结果
- **toolExecute**：执行工具
- **agentLoop**：循环执行任务直到任务完成

> 除此以外，需要将项目路径放置在system prompt里，便于Agent知道要操作的项目以及bash命令执行的路径。

### 执行示例

以下为一个执行示例：

- **第一条消息**为用户指令
- **第二条消息**为Agent输出：
  - 做出规划：1. 首先查看文件内容，了解数据结构 2. 然后计算这些数字的和
  - 进行决策：查看文件内容
  - 调用工具：执行bash工具 `{"command":"cat number.txt"}`
- **第三条消息**为Agent输出：
  - 查看工具执行结果
  - 进行决策：计算数字和
  - 调用工具：执行bash工具 `{"command":"awk '{sum=0; for(i=1;i<=NF;i++) sum+=$i; print sum}' number.txt"}`
- **第四条消息**为Agent输出：
  - 查看工具执行结果
  - 检查任务状态：任务完成
  - 输出结果：这些数字是：1+2+3+4+5+6+7+8=36。任务已完成。

> Agent连续执行了三次循环来完成任务，最后一次没有触发工具调用，此时任务结束，用户可继续输入下一条指令。

## 【5】Agent能力扩展

### 优化文件读写

claude code是一个编码智能体，因此需要构造出一台"电脑"让Agent操作，这里使用的是终端。终端是人与电脑交互的媒介，也可以是Agent与电脑交互的媒介。借鉴Linux的一切皆为文件思想，Agent通过终端操作文件与电脑交互，将这种交互抽象为5个能力：

1. 创建文件
2. 删除文件
3. 编辑文件
4. 搜索读取文件
5. 运行文件

这些能力通过定义工具来实现，前面已经构造 `bash` 工具，事实上它已经能完成所有的操作，但为了解决跨平台、运行性能、简化token输出、执行和输出稳定性等问题（cat 截断不可预测, sed 遇到特殊字符就崩），并且方便做一些其它的前置或后置处理，需要将高频使用的能力单独定义为工具，比如使用Ripgrep实现文件查找工具，提升查找性能，简化输出命令。

> 只有 bash 时，所有操作都走 shell，每次 bash 调用都是不受约束的安全面。专用工具（read_file、write_file）可以在工具层面做路径沙箱。

这里额外再定义最高频的三个文件相关工具，通过文件读写以及命令执行，能完成大部分编程任务：

#### `write_file`

- **功能**：使用新内容覆盖原文件内容或追加在原文件末尾
- **使用场景**：大批量修改和新增文件场景

#### `edit_file`

- **功能**：将文件中的指定字符串替换为新的字符串
- **使用场景**：少量修改文件中的部分内容

#### `read_file`

- **功能**：读取指定文件内容
- **使用场景**：读取文件内容

> 这里我们只实现最基本的能力来解决不同操作系统的命令差异问题，除此以外，还可在工具中添加文件diff、linter检查等功能，给Agent提供更丰富的上下文信息。

### 增强规划能力

在复杂任务中，随着上下文的增长，Agent可能逐步遗忘自己要做的事情，比如一开始规划了10步，可能在走完3-4步后，就会忘记后面要做的6-7步。

这里使用一种类似**草稿本**的机制，在适当的时候提醒Agent。Agent首先将规划的内容记录在草稿本上，在每次任务完成后更新任务的状态，使得规划的内容可以持续地出现在上下文末尾。

通过一个任务管理工具实现该能力：

#### `task_manage`

- **功能**：管理Agent要执行的任务，支持创建和更新任务，每次调用都返回当前所有任务信息，进一步，支持指定任务依赖，形成一个任务执行图，增强任务执行逻辑
- **使用场景**：Agent执行复杂任务时，需要提前规划子任务并随着执行更新任务状态

### 并发执行

部分任务执行可能需要等待长时间，甚至不会主动停止（如 `npm install` 或 `npm run dev` 命令），这会导致Agent长时间被阻塞。

可以将该任务放置在后台执行，在执行完毕后再通知Agent执行结果，实现任务并发。

将这些放置在后台执行的任务称为**后台任务(background task)**，有两种方式添加后台任务：

1. 改造bash工具，Agent可以通过传参来控制是否后台执行
2. 添加新命令，用户可以通过命令来将当前正在执行的任务转为后台任务

整体通过使用一个后台任务管理器来实现，将任务执行函数进行包装，如果未添加到后台任务，则阻塞直到任务执行结束，否则提前返回，向Agent说明任务在后台执行并给出后台任务id。

> 后台任务执行完毕后，其结果会被添加到已完成任务列表，在每次执行LLM调用前，清空已完成任务列表，将任务执行结果拼接在上下文中让Agent感知。

### 子代理模式

在任务初期，Agent为了解项目，可能会读取大量文件，导致占据大量上下文空间，但Agent只需知道项目目录结构以及每个模块的摘要信息。

可以采用**子代理模式**，Agent派遣一个子Agent去了解项目内容，子Agent会阅读大量代码文件，最后向Agent返回总结后的项目结构以及各模块功能即可。除此以外，Agent还可以同时派遣多个子Agent并行执行子任务，提升执行效率。

通过一个sub-agent工具实现该能力：

#### `sub-agent`

- **功能**：调用多个子Agent并行执行父Agent派发的任务
- **使用场景**：有多个可并行执行的任务；只关心任务结果，不依赖任务过程时

## 【6】构建无限上下文

上下文指输入给LLM的messages，有一个长度限制，计量单位为token，一个token可以近似看做一个字符，比如LongCat-Flash-Chat-Eco模型为128K token。在多轮任务后，messages的长度可能撑爆上下文窗口，无法继续对话。

为避免上下文溢出导致任务失败，需要使用**上下文缩减（context reduction）**技术来减少上下文长度，通常有两类策略：

1. **压缩**：通过启发式策略直接移除部分上下文，最简单的方式就是认为距离最新对话越远的消息越不重要，因此移除消息列表中前x%的消息记录。该方法简单、快速，但会丢失信息。
2. **摘要**：移除消息列表中前x%的消息记录，并通过LLM将这部分消息总结为简短的摘要添加到消息列表中。该方法能保留部分重要信息，但依赖LLM调用，因此时延长且成本高。

首先实现一个 `ContextCompactor` 来实现这两种缩减技术，需要注意的有两个点：

1. 摘要总结最好是结构化的，避免丢失重要信息（尤其是目标和执行计划）
2. 剩余未缩减的上下文最好保留完整的工具调用记录，使得整体逻辑连贯，保证Agent继续任务的稳定性

> 根据LLM调用接口返回值中的token消耗量，计算当前上下文长度是否超过阈值，并启用缩减。

## 【总结】

目前为止，我们已经搭建完一个完整的AI coding Agent框架，通过三个关键能力来自主完成coding任务：

1. **自主任务规划**并持续执行直到完成任务
2. 通过bash以及写文件工具可以实现任意文件的**查找、读取、修改**以及其它命令行程序的执行
3. 通过**上下文优化**避免在复杂任务中撑爆上下文导致任务失败

事实上，通过1、2、3步已经完成了一个初版Agent的构建，4、5、6步是为了使simple-code能有更好的性能以及更优的体验，其中隐含着打造出一个Agent应用的三个重要探索方向：

### 人机交互

权限控制体现了一种人机交互的方式，通过"是"和"否"的选择来让人介入Agent的任务执行过程。A2UI（Agent-to-User Interface）协议、cursor中的@指令等都是在人机交互方向的探索和工程实践。构建自然、高效、有温度的交互体验对于人机协同工作非常重要。

### Agent能力扩展

如何设计工具让Agent能在指定环境下具备完成任务所需的完备能力，如何让Agent能快速扩展工具，以及能精准且高效地调用工具等都是在这个方向要解决的问题。Skills、MCP等技术都是当前的重要探索成果。

### 上下文工程

构建无限上下文体现的是对Agent的上下文管理，LLM的输出依赖于输入上下文，模型的能力会受到上下文的两个限制：

1. 模型的上下文长度是有限的，无法塞入无限的信息
2. 模型存在上下文腐烂问题，随着上下文长度的增长，其输出会变得不可靠

如何更可靠的构建上下文直接关乎Agent的性能表现。因此，如何管理上下文是Agent应用中最为重要的难题，这需要一个复杂的系统架构设计，相关技术都归到上下文工程，后续会再写一篇文章论述当前上下文工程的进展。

> 除此以外，Memory、Multi-agents等技术也是一些正在探索的热门方向。

---

最后，任何技术都需要工程以及产品化落地，以向用户提供稳定且高效的使用体验，Simple-code只是一个最简单可运行版本，接下来会实现mini-claude-code（施工中），这里详细阐述了一个生产级应用的实现，基于simple-code进行了一系列的优化和扩展，包括更完备的提示词设置、更好的上下文处理策略，更便捷的交互以及MCP、SKILLS、RULES等扩展模块。
